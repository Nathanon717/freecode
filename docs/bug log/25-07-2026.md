# Three grep defects found while extending the tool: a file `path` crashed, a bad regex reported "No matches found", and a `:` in a filename mis-parsed

**Files:** `src/agent/tools/grep.ts`, `tests/agent/tools/grep.test.ts`, `tests/agent/tools/grep-mocked.test.ts`

Found by inspection and reproduced locally while adding output modes and context
lines. All three predate that work; none had coverage.

## 1. `path` naming a file crashed the search

`execute()` passed `resolved.fullPath` straight to `execFile`'s `cwd`. When `path`
named a directory that is correct, but the parameter was never restricted to
directories and the docs did not say so, so `grep(pattern="x", path="src/index.ts")`
— the obvious way to search one file — made Node spawn `rg` with a *file* as its
working directory. That rejects with `ENOTDIR`, which fell through to the outer
catch as `Error searching: spawn ENOTDIR`.

**Fix:** stat the resolved path first. A directory keeps `cwd = path`, target `.`;
a file becomes `cwd = dirname(path)`, target `basename(path)`.

The second half is not optional: rg **omits the filename from its output when given
a single file as its target**, so with a bare basename every result row would arrive
as `3:text` with no path, and the parser would drop all of it. `--with-filename` is
now passed unconditionally to force the path back on. Verified directly:

```
$ rg -n --no-heading -- NEEDLE a.txt
3:NEEDLE one
$ rg -n --no-heading --null --with-filename -- NEEDLE a.txt
a.txt\03:NEEDLE one
```

## 2. A malformed regex was reported as "No matches found"

The exit-code ladder treated **every** exit 2 as partial success and returned
`err.stdout ?? ''`, which for a usage error is empty — rendering as
`No matches found`. So `grep(pattern="foo(")` claimed the pattern legitimately
matched nothing, when in fact the search never ran.

The premise behind that branch was that `--no-messages` blanks stderr, so exit 2
could carry no detail. That premise is wrong — `--no-messages` suppresses only I/O
warnings (the unreadable-file case it was added for), not regex or usage errors:

```
$ rg --no-config -n --no-heading --no-messages -- 'foo(' .
rg: regex parse error:
    (?:foo()
    ^
error: unclosed group
exit=2
```

**Fix:** split the exit-2 branch on what is actually present. stdout → partial
results (unchanged). No stdout but non-empty stderr → `Search failed: <first 3
stderr lines>`. Neither → `No matches found`. This is the worst of the three
bugs: the other two produce a visible error, this one produced a confident wrong
answer that a model would act on.

## 3. A `:` in a filename mis-parsed the row

The parser split each row on the first two `:` characters, so `we:ird.ts:1:text`
yielded file `we`, line `NaN` — dropped by the `isNaN` guard. Silent under-reporting,
no error.

**Fix:** run rg with `--null`, which separates the path from the rest with a NUL
instead of `:`. The split is then unambiguous regardless of the filename.

`--null` was needed for the context-lines feature anyway (it keeps rg's match `:`
vs. context `-` separator distinguishable after the path is stripped), so this
fix came for free — but it is a real pre-existing bug and worth recording as one.

## Testing note

The mocked suite (`grep-mocked.test.ts`) stubs `fs/promises.stat` to control
mtime-based sorting. Fix 1 introduces a *second* caller of `stat` — the directory
probe — so a blanket `mockRejectedValue`/`mockResolvedValueOnce` now hits the wrong
call and breaks tests that have nothing to do with it. The mocks are now path-keyed
(`String(p).endsWith('index.ts')`) rather than call-order-keyed, and `beforeEach`
seeds a default resolving stat so tests that don't care about mtime are unaffected.
Call-order-keyed mocks were the fragile part; the ordering assertion in the
multi-file test is now stronger for it (it asserts the newer file renders first,
which the `mockResolvedValueOnce` version never actually checked).
