# An unwritable snapshot store silently disabled the one-delegation-at-a-time lock

**Files:** `src/snapshots/review-lock.ts`, `src/cli/headless-prompt.ts`

`claimReviewLock` returned `ReviewLock | undefined`, where `undefined` meant
*proceed*:

```ts
try {
  writeFileSync(path, JSON.stringify(mine), { flag: 'wx' });
  return undefined;                    // claimed
} catch {
  return readReviewLock(projectRoot);   // held… or undefined
}
```

The exclusive write fails for two unrelated reasons — the lock is held, or the
store cannot be written at all — and the readback was used to tell them apart.
When *that* also failed, the function returned `undefined`, which its caller reads
as "nobody holds it". So an unwritable snapshots directory, or a half-written lock
file, turned mutual exclusion off and started the run anyway: two `-p --edit`
delegations could overlap, and `checkpoint diff` would then answer about whichever
snapshot happened to be newer without saying so.

**Cause:** the comment said it was deliberate — "a broken safety net may not
become a broken freecode" — and that reasoning is right for
`ensureSnapshot`, whose failure must not block a write. It is backwards here. The
lock is not a net under the run; it is the precondition for the run being
reviewable at all, and "I cannot tell whether one is held" is the case where
proceeding is *least* defensible, because the store the review depends on is
already broken.

**Fix:** three outcomes instead of two, and only one of them proceeds.

```ts
type ReviewLockClaim =
  | { status: 'claimed' }
  | { status: 'held'; held: ReviewLock }
  | { status: 'unavailable'; cause: 'unreadable-lock' | 'store-unwritable';
      path: string; reason: string };
```

Fail-closed without a diagnosis only trades a silent hole for a mystery lockout,
so the refusal carries the path and the errno. It also carries `cause`, because
the two shapes of `unavailable` do not have the same fix — and one has no fix
inside freecode:

- **`unreadable-lock`** (a lock file really is at that path): there and
  unparseable, which is what a run killed mid-write leaves. Delete it.
- **`store-unwritable`** (no file there): `checkpoint accept` is documented as the
  way out of a stuck lock, but it takes a *baseline snapshot*, so it has to write
  the very store that just failed. Telling someone to delete a lock file here
  would send them after a file that does not exist.

The split is `existsSync`, not the errno, and the first attempt got that wrong:
`mkdirSync` raises `EEXIST` for a *file* sitting where the snapshots directory
belongs, so a broken store arrived wearing the errno of a held lock and was
misreported as a deletable one. Caught by the test for the case it misreported.

**Behaviour change worth knowing:** a half-written lock file now wedges
`-p --edit` until it is deleted by hand. Reading paths (`readReviewLock`, and so
`outstanding()`) still treat it as no lock, which is right — they act on a holder
they can see, and there is none.

**Not fixed here:** the lock file lives outside the project, so no guard covers
`rm` on it, and `rm -rf ~/.config/freecode/snapshots` still destroys every
snapshot for every project on the machine. Fail-closed makes an *accident*
loud; it does nothing about an agent that deletes the file on purpose. That is
containment's job (C1 in `docs/agent-containment-plan.md`), not the lock's.
