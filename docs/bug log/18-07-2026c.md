# Freecode launched outside the repo starts with an empty store

**Symptom:** running freecode via the `freecode` alias from any directory outside
the repo root gave a fresh-install session — no saved config, no provider
overrides, an empty model list. Launching from the repo root or any subdirectory
worked. No error was printed either way.

**Cause:** two independent faults in the launch wrapper, not in `src/`.

1. `doppler run --` resolves its project/config from the **current directory**,
   via the scope table in `~/.doppler/.doppler.yaml`. The scope was registered on
   the repo path, so it inherited into subdirectories but not outside. From
   elsewhere Doppler hit a bare drive-root entry with no project and reported
   `You must specify a project` — then ran the app anyway with an unpopulated
   environment, so the failure never surfaced.
2. The wrapper existed only as a **PowerShell profile function**. Launched from
   `cmd.exe` it did not exist at all, and `freecode` resolved to the raw npm shim
   with no Doppler in the chain.

Either path leaves `FREECODE_DB_SYNC_URL` / `FREECODE_DB_AUTH_TOKEN` unset, so
`readDbConfig()` returns empty and the tokenless-replica decline in `db.ts`
declines to open the existing replica (opening it as a plain client would dirty
the WAL and invalidate the `-info` sync metadata). `doInit` then degrades to an
empty in-memory cache. That decline is a deliberate, calm path — which is why the
whole chain is silent.

Confirmed by probing the real startup path from both directories: with secrets
injected, `getStoreDir()`, the config paths, the DB config cache and all 149
model rows were byte-identical inside and outside the repo. Without them:
`syncCfg {}`, `dbCache NULL`, 0 models. Nothing in `src/` reads `process.cwd()`
for store or config resolution — `getStoreDir()` derives from `import.meta.url`
and `getConfigDir()` from `homedir()`.

**Fix:** documentation only — no source change. `docs/device-setup.md` now pins
`-p freecode -c dev` in every wrapper form, recommends a `PATH` `.cmd` wrapper on
Windows so every shell is covered rather than PowerShell alone, and documents
this failure mode with a one-line check for whether secrets are arriving.

**Follow-up (not done):** the degradation is silent by design, which cost several
rounds of diagnosis. A TTY-gated warning when an `-info` sidecar exists but tokens
do not would make this self-diagnosing.
