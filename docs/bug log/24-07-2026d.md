# Root-directory grep failed with an opaque `Command failed`, while the same search in a subfolder succeeded

**Files:** `src/agent/tools/grep.ts`, `tests/agent/tools/grep-mocked.test.ts`

Reported from a live session against an external C# solution
(`C:\pTools4\Teravera.AI\Development`). Searching the project root:

```
grep(OpeningMessage)
  Error searching: Command failed: ...\rg.exe --no-config -n --no-heading --hidden --glob=!.git/* --no-messages -- OpeningMessage .
```

while the identical search scoped to a subfolder returned 11 matches. The
surprising part was the shape: a root search is a superset of the subfolder
search, so it should not fail where the narrower one succeeds.

**Cause:** the root search never completed — `execFile`'s `timeout: 10000` killed
`rg` mid-traversal. A signalled child has `code === null`, so it fell through
`grep.ts`'s `if (e.code === 1) / if (e.code === 2)` ladder into `else throw err`.
Because `--no-messages` blanks stderr, `execFile`'s rejection message degrades to
bare `Command failed: <cmd>\n`, which the outer catch surfaced verbatim. Nothing
in the message said "timeout".

Elimination, all reproduced locally against the real directory:

- **exit 1** returns `No matches found` — not this.
- **exit 2** (unreadable files) is handled and returns matches. Confirmed by
  exclusive-locking a `.vsidx` file with `[System.IO.File]::Open(..., 'None')`:
  rg exits 2 *even with* `--no-messages`, and the tool's `e.stdout` path
  recovers the results. The `os error 32` lines on the user's `.vs\FileContentIndex`
  files were a red herring.
- **maxBuffer overflow** rejects with `code: 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'`
  and message `stdout maxBuffer length exceeded` — a different string.
- **timeout kill** reproduces the message byte-for-byte: `code=null`,
  `signal='SIGTERM'`, `killed=true`, message `Command failed: <cmd>\n`.

Only the last one is left. Note this is elimination, not reproduction: every run
against the real directory *succeeded* (exit 2, ~1.4s warm, `rg --stats`: 30,147
files, 1.53 GB), so the original event was never reproduced byte-for-byte. The
inference is that it was a cold and/or disk-contended first touch — the locked
`.vs\FileContentIndex` files show Visual Studio was actively working the same
tree at the time — and 1.4s warm leaves ample headroom to cross 10s cold under
Defender plus a concurrent build. The signature itself is decisive regardless:
no other rejection produces `Command failed` with an empty tail.

**Aggravating factor:** the directory has a `.gitignore` but **no `.git`**.
ripgrep only applies `.gitignore` inside a git repository, so nothing pruned
`bin`/`obj`/`.vs` — hence `obj\Debug\net10.0\functions.metadata` in the results.

**Fix:** handle the two non-exit-code rejections before the exit-code ladder and
return an actionable string instead of rethrowing:

- `e.killed || e.signal` → `Search timed out after 10s. Narrow it with a more
  specific "path" or an "include" glob.`
- `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` → `Search produced more than 10MB of
  output. Narrow it with ...`

The timeout and buffer limits are now named constants (`TIMEOUT_MS`,
`MAX_BUFFER`) so the message and the option can't drift apart. `else throw err`
is kept for genuinely unexpected exits — rg only ever exits 0/1/2, so that branch
now means something is actually wrong.

This is the diagnostic fix, not a performance fix: a cold root scan of a large
tree can still exceed 10s, but it now says so instead of printing
`Command failed`. Raising the timeout was deliberately rejected — it only makes
the caller wait longer for the same wall.

**Second fix — `--no-require-git`:** added so `.gitignore` is honored in trees
that have one but no `.git`. On the reported directory this drops the walk from
30,147 to 22,601 files; it is only ~80 MB less, so it is a correctness fix (stop
returning build artifacts the ignore file already excludes) more than a speed
one, and will not by itself prevent a cold timeout.

Tradeoff worth knowing: the flag ungates *every* git ignore source, not just the
tree's own `.gitignore` — including the global `core.excludesFile`
(`~/.config/git/ignore`, which exists on this machine). So in a non-git tree grep
now also skips paths matched by rules that live outside it. Accepted: it is the
same rule set the user already gets inside any repo.

Testing this needed care: a fixture under `tests/` passes with or without the
flag, because it sits inside freecode's own checkout where `.gitignore` applies
anyway. The regression test uses `mkdtemp(tmpdir())` plus `setProjectRoot` to get
a genuinely git-less root, and was verified to fail with the flag removed.

**Follow-up (not done):** hard-pruning heavy directories (`node_modules`, `bin`,
`obj`, `.vs`, `dist`) regardless of ignore files. Rejected for now — it bakes in
opinions and makes those paths unsearchable without an override.
