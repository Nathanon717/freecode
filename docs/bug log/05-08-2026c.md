# 05-08-2026c — A failing `dotnet build` reported nothing but `Error: Command failed: dotnet build`

## Symptom

Reported from a real session. The agent ran `dotnet build`, the build failed with
compiler errors, and the entire tool result the model received was:

```
Error: Command failed: dotnet build
```

Not one diagnostic. The model had no way to know what to fix, and no way to know
what "failed" even meant.

## Cause

`shell.ts`'s catch block returned `error.message` and nothing else. That looks
like it preserves the failure output, and for a stderr-reporting command it
does — but only by accident. `child_process.exec` rejects with:

```
message = "Command failed: <cmd>\n" + stderr    ← stderr, folded in
stdout  = "<everything the command printed to stdout>"    ← dropped on the floor
stderr  = "<same text already in message>"
code    = 1
```

Verified directly, not inferred. So the bug is **not** "output was lost" — it is
that *stdout specifically* was lost. `dotnet build` writes its compiler
diagnostics to stdout, as do `tsc`, `msbuild`, and most of the MSBuild family, so
for exactly the tools an agent runs most this discarded 100% of the useful text
while looking like it had preserved it.

Two adjacent kills produced the same annihilated result. `exec`'s default
`maxBuffer` is 1 MB — a real `dotnet build` or `npm test` exceeds it, the child is
killed, and the error carries the same dropped stdout. And a timeout SIGTERMs the
child, whose partial output was likewise thrown away.

This is the same defect [24-07-2026d.md](24-07-2026d.md) fixed in the grep tool
(timeout and maxBuffer kills reported as an opaque `Command failed`). That fix
was applied to `grep.ts` only; `shell.ts` had it all along.

## Fix

The result is now the command's own bytes and nothing else, plus a trailing
status line **only when the status is not already implied by those bytes**.

The discriminating question is whether the model can tell success from failure
from the output alone. It cannot: `dotnet build` prints errors to stdout and
exits 1, while plenty of commands print alarming text and exit 0. Exit status is
information that is not in the output, so it must be carried separately —
`[exit 1]`, `[timed out after 30000ms: ...]`, `[output exceeded ... bytes: ...]`,
`[command did not run: ...]`.

The one case where a bare empty result would be wrong is success with no output:
blank alone is indistinguishable from a *failure* that printed nothing, so that
case returns `[exit 0, no output]`. A clean exit that did produce output gets no
status line at all — the output speaks for itself.

`maxBuffer` raised to 10 MB in the same change, since the 1 MB default destroys
output for the same commands and via the same mechanism. Capturing 10 MB is not
the same as sending it, though, so the result the model receives is capped at
100k characters — a 60k head plus a 40k tail, the shape that keeps a failing
build's first diagnostics *and* its summary. `grep.ts` already truncates its
results with an explicit notice; without a cap here `shell_exec` would have been
the one tool able to spend the whole context window on a single call. The
elision is always stated, and the status line is appended after elision so it
can never be the part that gets dropped.

Deliberately unchanged: the `confirmDestructive` refusal string, which is a
refusal rather than a command result. Deliberately not attempted: true
stdout/stderr interleaving — `exec` returns two separate buffers and only a pty
would preserve ordering.

## Coverage

- `tests/agent/tools/shell.test.ts` — stdout survives a non-zero exit (the
  reported bug, asserting `Command failed` is *absent*); stderr and exit code
  both reported; a failure with no output at all still says `[exit 2]` rather
  than going blank; 2 MB of stdout is captured past the old 1 MB `maxBuffer`
  and windowed to the cap with both ends intact; output under the cap stays
  byte-exact; and an elided failure still ends in `[exit 1]`.
- `tests/e2e/shell-failure-output.e2e.json` — end to end. The fixture's turn-2
  matcher requires `BUILD_FAILED_ON_STDOUT` and `[exit 1]` in the message
  history, so it asserts the *model* received the build output, not merely that
  the transcript rendered it.
