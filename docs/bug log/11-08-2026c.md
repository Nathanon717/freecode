# The unit section of `npm test` was buried in stack traces from tests that pass

**Files:** `src/logger.ts`, `vitest.config.ts`, `tests/logger.test.ts`

A green run — 134 files, 3276 passing — printed nine stack traces and shredded the
dot reporter into fragments:

```
[15:24:33.416] [error] [db] Store init failed; continuing without persistence: ConnectionFailed(...)
Error: ConnectionFailed("Unable to open connection to local database ...")
    at new Database (C:\Dev\freecode\node_modules\libsql\index.js:95:17)
    ...
························································································
[15:24:35.511] [error] [registry] Failed to fetch zen models, using cache: Network failure
```

Every line carried the `[error]` tag, so all of it was `logError` and none was `log()` —
`log()` is already a no-op until `enableLog()`. The writes came from tests doing their job:
`db.test.ts` proving a store that cannot open still starts, `provider-registry.test.ts`
proving a 500 falls back to cache, `parsed-tools.test.ts` proving malformed JSON in a
`<tool_call>` block is survivable. The errors were expected. Their output was not.

Two facts made this look worse than an ordinary noisy log:

- `logError` wrote unconditionally, by design — `@readwhen` said so, and a test named
  *"writes even when not enabled, so errors are never swallowed"* pinned it.
- Those writes bypass vitest's capture. There are no `stderr | tests/…` headers anywhere
  in the output; the worker's `process.stderr.write` goes straight to the parent's real
  stderr, interleaving with the reporter as it draws. That is why the dots break into
  runs — not a reporter bug, just two writers on one stream.

## Fix

`logError` now returns early when `FREECODE_SILENCE_ERRORS` is set, and `vitest.config.ts`
sets it alongside the `FREECODE_TRANSCRIPT_STREAM` it already carried.

The rejected alternative was a `setupFiles` stub of `process.stderr.write`. It would have
worked and touched one file, but it silences *everything* a worker writes — including the
diagnostics of the test that is actually failing, which is the one moment the output
matters. Gating the logger keeps the mute to expected noise.

`FREECODE_SILENCE_ERRORS` is read at call time rather than module load, so
`tests/logger.test.ts` can `vi.stubEnv(..., undefined)` in `beforeEach` and go on asserting
the real write path; two new tests cover the silenced path and the per-call re-read. Gating
on `VITEST` instead would have left that file no way to opt out.

`npm run test:e2e` runs through `tsx tests/harness/run-e2e.ts`, not vitest, so the config
`env` never reaches it and e2e stderr assertions are untouched.

## Why this is not [10-08-2026c.md](10-08-2026c.md) again

That entry is a gate on `logError` being re-added by accident and swallowing real errors for
two months; [10-08-2026d.md](10-08-2026d.md) is the bug it hid. This adds a gate to
`logError`. The difference is what the gate keys on and who can turn it on:

- The old one keyed on `enabled` — the `-log` flag. It was **on by default in production**:
  every user running `freecode` without `-log` lost their errors.
- This one keys on a variable nothing sets but `vitest.config.ts`. A real run has it unset
  and behaves exactly as before.

`@role` still promises errors surface, now with the exception named, so `intent-drift` — which
is what caught the old one — reads the tag against a gate the code actually has. The old
regression was invisible because the only mention of it was a test asserting the wrong thing.
The risk that remains is the same shape as `10-08-2026d.md`: a genuine bug that only ever
announces itself through `logError` will now stay quiet **inside the unit suite**. That is
the accepted cost, and it is bounded — e2e keeps its stderr, and a production run is untouched.

That bound has one condition worth knowing: `run-e2e.ts` builds each subprocess env from
`process.env` (minus provider keys), so it *inherits*. It is safe today only because the
variable lives in `vitest.config.ts`, scoped to the vitest process — the e2e section is a
separate spawn that never sees it. Set `FREECODE_SILENCE_ERRORS` anywhere higher, in
`scripts/pipeline/` or a shell, and e2e goes quiet with it.
