# 05-08-2026 — Esc at a tool approval: first it discarded the whole turn's completed work, then it would not stop the turn

Two rounds on the same bug, same day. The first fix stopped Esc destroying the
turn; it also left the turn unbounded, which had to be fixed on top. What the code
does now is under [Fix](#fix); the first design is kept below it because its
reasoning is still the reason the current one is shaped the way it is.

## Symptom

**Round 1.** Reported as: denying a tool call seems to wipe conversation history —
not visually (the transcript still shows everything that happened), but the model
starts fresh from the next message, as if the exchange never happened.

Confirmed via a 3-turn TTY fixture (turn 1 completes, turn 2 aborts at an
approval, turn 3 probes `messageCount`): turns committed *before* the aborted
one survive intact. Only the aborted turn's own contribution is lost — but that
turn could include several already-completed tool calls (real reads, edits,
shell commands) if the model called more than one tool before the user denied
the last one. All of it, plus the user's own message, vanished from history —
matching the report for any turn only a couple of exchanges deep.

**Round 2**, reported from a real session after the first fix shipped. Esc on a
`shell_exec` approval printed the denial, and then — with no user input in
between — the agent produced a *second* tool call, which appeared already denied
with a longer message, and then a final answer:

```
shell_exec(dotnet build …)
  Tool call denied by user: shell_exec(dotnet build …)

The user denied that call. Let me try running the test command directly …
shell_exec(dotnet test …)
  Tool call denied by user: shell_exec(dotnet test …)
  User input after denial: The user pressed Esc to stop this turn. Do not make further tool calls — wait for new instructions.

All changes are complete. Here is a summary of what was done …
```

Two extra model calls after the user asked to stop, and the stop instruction only
reached the model *after* it had already tried something else.

## Cause

Esc at a tool-approval prompt (`cli/tools/tool-approval.ts`) threw
`UserAbortError` from inside the tool's `execute()`. `withToolRendering`
(then in `agent/tools/index.ts`) special-cased it to rethrow instead of converting
it to a result string, so it unwound the entire `streamText` attempt —
`runRecoveringStream` (`agent/stream-turn.ts`) only collects `turnMessages`
from an attempt that *drained*, so a throw anywhere in the attempt discarded
every step's messages, not only the one being denied. `agentLoop`'s
`isUserAbortError` catch then returned `finishResult(fullText)` with
`turnMessages: []`, and `Conversation.commitTurn` — correctly, given empty
input — committed nothing at all ([28-07-2026.md](28-07-2026.md), whose fix this
built on but never anticipated a multi-step turn aborting past its first
call).

The single existing regression test (`tty-abort-no-orphan.e2e.json`) only
covered the simplest shape: Esc on the very first, and only, tool call in the
turn. That happens to make the loss invisible, since there was nothing earlier
in the turn to lose.

The round-2 behaviour was the first fix (below) working exactly as written. It
replaced the throw with an ordinary denial so the turn's completed work would stop
being discarded — and an ordinary denial is a tool *result*. The AI SDK continues
a turn whenever every tool call in the step has a result (`maxSteps` is
unlimited), so the denial bought exactly one more model call.
`cli/session-modes.ts` then auto-denied whatever that call proposed, which bought
another. **"Every further call this turn is auto-denied" was never a bound on the
turn:** a model that keeps proposing tools keeps being asked, with no key the user
can press.

The Esc'd call itself also carried no message — the stop text was attached only
to the *auto-denials that followed*, which is why the model's first signal was a
bare "denied" and its natural next move was to try an alternative.

Two smaller faults fell out of the same design: `stopRequested` was reset only
in `beforeAgentCall`, which hand-typed tool calls (`command-dispatcher.ts`) never
run — so an Esc leaked past the end of the turn and silently auto-denied the next
hand-typed call; and `docs/map/cli/session-modes.md` claimed a turn was bounded
by "every remaining call being auto-denied after an Esc", which it was not.

## Fix

Esc now ends the turn. The denial keeps its shape — same
`Tool call denied by user: …` result, rendered the same way, committed the same
way (one sentence is appended; see below) — but `ToolCallConfirmation` gained
`stopTurn`, and a new `withTurnStop` wrapper (`agent/tools/wrappers.ts`) throws
`TurnStoppedError` once that result has rendered.

**The throw is the mechanism.** `ai@3.4`'s `streamText` only takes another step
when `stepToolResults.length === stepToolCalls.length`; a rejected `execute`
leaves one call without a result, so the stream finishes gracefully —
`finishReason: 'error'`, `responseMessages` resolved, no further model call. Its
position in the stack is load-bearing in both directions: outside
`withToolRendering` (which converts throws into `Error: …` results) so the denial
still prints, and inside `withSerializedExecution` so a sibling call queued behind
it throws on entry instead of prompting.

The cost is one unpaired tool call in `responseMessages`, and that is precisely
the shape that made round 1 destructive: `dropUnpairedToolCalls` strips
it, the turn sanitizes to nothing, and `Conversation.commitTurn` drops the user's
own message with it. So `agent/turn-messages.ts` gained `pairStoppedToolCalls`,
which gives the stopped call back the denial text that was already rendered for
it, by `toolCallId`, before anything else sees the turn.
`agent/stream-turn.ts` recognises the sentinel in the stream's `error` part and
reports it as `stopDenials` rather than a failure — checked *before* the
rejected-tool-call recovery path, so a stopped turn is never retried. The two
text-protocol loops (`agent/parsed-tools.ts`, `agent/fake-loop.ts`) catch it in
`executeToolCalls`, keep the denial as that call's result, and end their loop.

`AgentLoopResult.stopped` carries it out, so `command-dispatcher.ts` prints
`Stopped. Send a message to continue.` instead of reporting the (expected) lack
of a closing answer as `(empty response from model)`.

The denial the model reads on its *next* turn gains one factual sentence —
`The user pressed Esc to stop the turn here.` — appended after the usual
`Tool call denied by user: …`. Not an instruction: the turn is already over. It
is there because a bare denial is indistinguishable from a plain Deny, whose
natural reading is "not *that* call", so a model mid-task re-proposes the call
the user just interrupted — the reported behaviour, displaced by one turn. The
old text was wrong for a different reason: it told the model to stop making tool
calls *while the turn was still running and still making them*, and it was
attached only to the auto-denials that came after the Esc, never to the Esc'd
call itself.

`cli/session-modes.ts`'s `stopRequested` flag is **deleted**, not patched: once
the turn really stops there is nothing left to auto-deny, and the `TurnStopState`
box that replaces it is created per `createTools()` — i.e. per turn — so it
cannot leak into a later hand-typed call.

`src/agent/tools/index.ts` crossed the 500-line limit with `withTurnStop` added,
so the whole decorator layer moved to `src/agent/tools/wrappers.ts`
([docs/map/agent/tools/wrappers.md](../map/agent/tools/wrappers.md)), leaving
`index.ts` owning only which tools exist and which a turn is offered.

**Rejected: `abortSignal` on `streamText`.** Aborting after the denial makes the
next `startStep` reject inside the transform's `flush`, which errors the stream —
`resolveResponseMessages` is never called, so `await stream.responseMessages`
hangs forever and the turn's messages are lost anyway. The graceful `done` branch
reached by a missing tool result resolves usage, response messages, and finish
reason unconditionally; that is the only exit that keeps the turn.

## The first fix, and what it got right

Round 1 shipped this: `confirmToolCallInteractive` resolves
`{ approved: false, escaped: true }` instead of throwing, and `withConfirmation`
returns "Tool call denied by user: …" as an ordinary paired tool result, so the
step (and the turn) drains normally and commits like any other turn. **That half
stands** — it is still how the denial reaches the model, and it is why completed
steps survive.

`UserAbortError`/`isUserAbortError` had no other real producer (the checks in
`agent/loop.ts`, `agent/fake-loop.ts`, `agent/tools/index.ts`, and
`cli/tools/tool-runner.ts` all existed only to special-case this one throw
site), so all four were removed along with the throw, and the class itself
deleted from `util/errors.ts`. Only the *abort branch* went in
`cli/tools/tool-runner.ts` — its surrounding `try/catch` stays, because it also
reports any other throw as a red `Error: …` line, and nothing between it and
`runCliSession` catches, so letting a throw escape would end the REPL over one
hand-typed call. `agent/subagents/run-subagent.ts` had the same check even though
sub-agents run raw, unwrapped read-only tools with no confirmation step at all —
never actually reachable — removed too.

The half that was wrong is the `escaped` flag and what read it: a per-turn
`stopRequested` in `cli/session-modes.ts` that auto-denied every further tool call
in the same turn without a prompt. See the second half of [Cause](#cause).

**Rejected in round 1: keep the throw but capture partial `turnMessages` before
rethrowing.** The denied call's own `execute()` never resolves on the throwing
path, so it has no paired result to sit in `stream.responseMessages` —
reconstructing a valid partial history would mean re-deriving the same
sanitizing `dropUnpairedToolCalls` already does, for a call that a plain
denial handles for free.

## Coverage

- `tests/e2e/tty-esc-deny-stops-turn.e2e.json` — text path. The fixture defines
  only two model calls for the whole scenario; turn 2's matcher requires the
  user's *second* message. A mid-turn call would take that slot with the denial
  as its last user message and fail there, so this asserts "the model was not
  called again" directly rather than through the screen. *(Shipped in round 1 as
  `tty-esc-deny-continues-turn`, pinning the follow-up step that turned out to be
  the bug; renamed when the follow-up stopped happening.)*
- `tests/e2e/tty-esc-deny-stops-turn-native.e2e.json` — the same on the native
  AI SDK path, where all the subtlety is. Its `messageCount: 4` is what proves
  `pairStoppedToolCalls` ran: without it the assistant tool-call message is
  stripped and the turn — user message included — commits nothing.
- `tests/e2e/tty-esc-deny-preserves-earlier-steps.e2e.json` — the round-1
  regression test, unchanged in intent and retargeted at the new turn count: an
  approved `list_dir` call completes, a second `create` call in the *same* turn is
  then Esc-denied, and the next turn's `messageCount` proves the completed
  `list_dir` step survived the later denial.
- `tests/agent/fake-loop.test.ts` — a denial carrying `stopTurn` ends the turn
  and still commits; the fixture's unreachable second step would throw if the
  model were called again. A *plain* denial still resolves the step and lets the
  turn continue.
- `tests/agent/tools/wrappers.test.ts` — the wrapper stack's own tests, moved
  out of `index.test.ts` with the code: `stopTurn` rejects with the rendered
  denial as `denialResult`, a sibling call is refused without ever reaching the
  approval callback, a plain denial does *not* stop the turn, and a fresh
  `createTools()` starts unstopped.
- `tests/cli/tools/tool-approval.test.ts` — Esc resolves
  `{ approved: false, stopTurn: true }`.
