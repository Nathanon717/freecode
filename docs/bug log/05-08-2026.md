# 05-08-2026 — Escaping a tool approval mid-turn discarded every completed step in that turn, not just the pending call

> ⚠️ **Partly superseded by [05-08-2026b.md](05-08-2026b.md).** The diagnosis
> below still holds and the "don't unwind the turn" half of the fix still stands.
> The other half — "the model is told to stop and every further call this turn is
> auto-denied" — was wrong: an auto-denial is still a tool result, so the model
> was called again for each one, and the turn had no bound at all. Esc now ends
> the turn outright. Read the sections below as history; `05-08-2026b.md` describes
> what the code does.

## Symptom

Reported as: denying a tool call seems to wipe conversation history — not
visually (the transcript still shows everything that happened), but the model
starts fresh from the next message, as if the exchange never happened.

Confirmed via a 3-turn TTY fixture (turn 1 completes, turn 2 aborts at an
approval, turn 3 probes `messageCount`): turns committed *before* the aborted
one survive intact. Only the aborted turn's own contribution is lost — but that
turn could include several already-completed tool calls (real reads, edits,
shell commands) if the model called more than one tool before the user denied
the last one. All of it, plus the user's own message, vanished from history —
matching the report for any turn only a couple of exchanges deep.

## Cause

Esc at a tool-approval prompt (`cli/tools/tool-approval.ts`) threw
`UserAbortError` from inside the tool's `execute()`. `withToolRendering`
(`agent/tools/index.ts`) special-cased it to rethrow instead of converting it
to a result string, so it unwound the entire `streamText` attempt —
`runRecoveringStream` (`agent/stream-turn.ts`) only collects `turnMessages`
from an attempt that *drained*, so a throw anywhere in the attempt discarded
every step's messages, not only the one being denied. `agentLoop`'s
`isUserAbortError` catch then returned `finishResult(fullText)` with
`turnMessages: []`, and `Conversation.commitTurn` — correctly, given empty
input — committed nothing at all (`docs/bug log/28-07-2026.md`, whose fix this
built on but never anticipated a multi-step turn aborting past its first
call).

The single existing regression test (`tty-abort-no-orphan.e2e.json`) only
covered the simplest shape: Esc on the very first, and only, tool call in the
turn. That happens to make the loss invisible, since there was nothing earlier
in the turn to lose.

## Fix

Esc now denies the pending call the same way an explicit "deny" always did —
`confirmToolCallInteractive` resolves `{ approved: false, escaped: true }`
instead of throwing. `withConfirmation` returns "Tool call denied by user: …"
as an ordinary paired tool result, so the step (and the turn) drains normally
and commits like any other turn.

The `escaped` flag is read only by `cli/session-modes.ts`'s `confirmToolCall`
wrapper, which sets a per-turn `stopRequested` flag (reset in
`beforeAgentCall`) and auto-denies every further tool call in the same turn
without a prompt — checked before read-only enforcement and Ask-mode, so it
always wins. This keeps Esc's actual intent (stop the agent, let me redirect)
without needing to unwind the stream: the model is told to stop and, absent a
tool it can still try, has nothing left to do but respond and end the turn.

`UserAbortError`/`isUserAbortError` had no other real producer (the checks in
`agent/loop.ts`, `agent/fake-loop.ts`, `agent/tools/index.ts`, and
`cli/tools/tool-runner.ts` all existed only to special-case this one throw
site), so all four are removed along with the throw, and the class itself is
deleted from `util/errors.ts`. Only the *abort branch* goes in
`cli/tools/tool-runner.ts` — its surrounding `try/catch` stays, because it also
reports any other throw as a red `Error: …` line, and nothing between it and
`runCliSession` catches, so letting a throw escape would end the REPL over one
hand-typed call. `agent/subagents/run-subagent.ts` had the same
check even though sub-agents run raw, unwrapped read-only tools with no
confirmation step at all — never actually reachable — removed too.

**Rejected: keep the throw but capture partial `turnMessages` before
rethrowing.** The denied call's own `execute()` never resolves on the throwing
path, so it has no paired result to sit in `stream.responseMessages` —
reconstructing a valid partial history would mean re-deriving the same
sanitizing `dropUnpairedToolCalls` already does, for a call that a plain
denial handles for free.

## Coverage

Retargeted by [05-08-2026b.md](05-08-2026b.md) — see its own Coverage section for
the current scenarios. As shipped here:

- `tests/e2e/tty-esc-deny-continues-turn.e2e.json` — single-call case: Esc on
  a tool call with no preamble, model gets a follow-up step, next turn's
  `messageCount` (4, not the pre-fix 1) proves the denial and its follow-up
  both committed. *(Renamed to `tty-esc-deny-stops-turn` once the follow-up
  step stopped happening — it was pinning the bug.)*
- `tests/e2e/tty-esc-deny-preserves-earlier-steps.e2e.json` — the actual
  regression: an approved `list_dir` call completes, a second `create` call in
  the *same* turn is then Esc-denied, and the next turn's `messageCount`
  proves the completed `list_dir` step survived the later denial. *(Still the
  live regression test, retargeted at the new turn count.)*
- `tests/agent/fake-loop.test.ts` — a denied tool call resolves the step
  instead of throwing, and the turn continues. *(Still true of a plain denial;
  an Esc denial now carries `stopTurn` and ends the turn.)*
- `tests/cli/tools/tool-approval.test.ts` — Esc resolves
  `{ approved: false, escaped: true }` rather than rejecting. *(The flag is now
  `stopTurn`, and it lives on `ToolCallConfirmation` itself.)*
