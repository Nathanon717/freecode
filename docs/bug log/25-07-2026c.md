# 25-07-2026c — A tool call the SDK rejected killed the whole turn instead of going back to the model

## Symptom

A single bad tool call ended the agent's turn. The user saw an error printed to the
terminal and the agent stopped, mid-task, with no chance to correct itself. The reported
case was `grep` — plausible because `067f843` gave it an enum and two numeric parameters,
widening the surface for a schema mismatch (`head_limit: "50"`, `output_mode: "files"`).

## Cause

Three failure classes never produce a tool result on the native path:

- **Invalid arguments** — `parseToolCall` throws `InvalidToolArgumentsError` before the
  tool's `execute` ever runs, so the tool itself never sees the call. Every path in
  `grep.ts` already returns an error *string*; schema rejection was the only way it could
  kill a turn.
- **Unknown tool name** — `NoSuchToolError`, same story.
- **A rejecting `execute`** — `withToolRendering` rethrew.

The AI SDK reports all three as an `error` part on `fullStream` and refuses to continue
the multi-step loop (`nextStepType` only advances when
`stepToolResults.length === stepToolCalls.length`). `loop.ts` rethrew the error part after
draining, ending the turn.

The recovery that existed made the mid-turn case worse rather than better. It set
`activeMessages = [...messages, feedback]` — the *original* history plus a nudge — so tool
calls already completed in that turn were absent from what the model saw next, putting a
non-idempotent one at risk of re-running (`shell_exec` re-executes, `create` fails on
`flag: 'wx'`, `edit` fails with "old_text not found"). The `fullText.length === 0` guard
covered only the `tool_use_failed` branch; the two tool-call branches instead did
`fullText = ''`, i.e. they were written for a first-token failure and simply discarded
accumulated output when they fired later. The budget was also one retry per turn shared
across all three classes, so a second bad call anywhere ended the turn outright.

Notably `parsed-tools.ts` had always done the right thing: `executeToolCalls` hands an
unknown tool and a failing `execute` straight back to the model as result text and keeps
looping. The native path was the odd one out.

## Fix

- `withToolRendering` (`agent/tools/index.ts`) returns `Error: ...` instead of rethrowing,
  so a failing tool becomes that call's result. User aborts still propagate. This also
  removes the orphan-`tool_use`-with-no-`tool_result` hazard that would break the next
  request to Anthropic. `executeToolCalls` no longer needs its own catch.
- `rejectedToolCall(error)` in `util/errors.ts` classifies both rejection kinds and returns
  the name, the arguments the model sent, and the feedback to hand back — shared so the two
  native tool loops cannot drift.
- `agent/loop.ts` recovers rejected calls mid-turn instead of restarting: it renders the
  rejected call like any other tool call (header + red failure line, written while the
  step is still open so it lands before the step divider), then continues from
  `result.responseMessages` — which resolves even after an error part and contains only
  calls that actually ran, each paired with its result — plus a message naming the tool
  and what was wrong. Nothing already executed is replayed. The budget is
  `MAX_REJECTED_TOOL_CALLS = 8` per turn, enough to recover repeatedly but still bounded
  against a model looping on the same broken call.
- The whole-turn restart is kept only for `tool_use_failed`, a provider-level rejection of
  the entire response, where `fullText.length === 0` means there is nothing partial to keep.
- Usage is carried across a recovered stream (`carriedTotalTokens` / `carriedOutputTokens`)
  since the turn now spans more than one `streamText` call.
- `subagents/run-subagent.ts` had the same defect, and worse: `runNativeSubAgent` drained
  `fullStream` without reading `error` parts at all, so *any* stream failure silently
  truncated the sub-turn and whatever text had accumulated was returned to the parent as
  findings. It now reads them, recovers rejected calls the same way, and rethrows anything
  else so `runSubAgent`'s catch surfaces a visible `Error: the <agent> sub-agent failed: …`.

`loop.ts` crossed the 500-line limit on the way, so the `mock:*` fixture turn moved to
`agent/fake-loop.ts` (with its tests) — a genuinely separate concern: it is the only path
that never touches the AI SDK.

## Coverage

`tests/e2e/agent-tool-arg-error-native.e2e.json` drives both branches in one turn through
the fake native provider: a namespaced tool name (`repo_browser.grep`), then `grep` with
`head_limit: "fifty"`, then a valid `grep`, then the final answer. It asserts the model
received each rejection (fixture `mustContain` on the feedback text), that only the valid
call reached the tool trace, and that the turn finished at exit code 0.
