# 28-07-2026b — Startup banner jumped up 3 rows the moment the footer/input UI painted

## Symptom

Launch freecode. The banner paints at the top of a cleared screen, correctly
positioned — then the rest of the chrome draws and the banner visibly shifts
upward, its top rows scrolling off into scrollback.

Reproduced through a real PTY at 100×24 with a model configured. The screen after
the prompt went live:

```
 1|  //     .d888                                                888             //
 2|  //    d88P"                                                 888             //
 ...
10|  //////////////////////////////////////////////////////////////////////////////
```

Row 1 should be the banner's blank lead-in, row 2 its top border. Both, plus the
`//   //` row under them, are gone — a 3-row shift. (Reported as "1 line"; the
measured shift is 3.)

Without a model configured the same run also lost the
`No model selected. Use /model to choose one.` line, which had been written *on
top of* the banner's first row before scrolling away.

## Cause

Two independent defects, one visible only because of the other.

**1. `setScrollRegion` homes the cursor, and `setupFooterUI` didn't account for
it.** DECSTBM (`\x1b[1;22r`) moves the cursor to (1,1) as part of setting the
region. `setupFooterUI` wrote it bare:

```ts
setScrollRegion(1, rows() - 2);
drawFooter();
```

`drawFooter` then saved (1,1) and restored (1,1), so the cursor was left at the
top of the screen with the banner already occupying rows 1–14. Every later
`console.log` therefore started overwriting the banner instead of continuing
below it. The raw trace shows exactly that:

```
[1;22r][s][23;1H][2K][24;1H][2K]…[u]«No model selected. Use /model to choose one.»
```

**2. `setupInputUI` scrolled a fixed 3 rows regardless of what was on screen.**

```ts
process.stdout.write(`${ESC}${r - footerRowCount};1H\n\n\n`);
```

The absolute move parks the cursor on the *bottom row of the scroll region*, so
all three newlines scroll unconditionally. That is right when output already
fills the region — the input frame would otherwise overwrite the last three
lines. It is wrong on a fresh screen, where rows 15–22 are empty and nothing
needs to move.

The two compose: fix 2 alone would stop the shift, but the cursor would sit near
the top and the banner would still be clobbered by the next `console.log`.

## Fix

**`setupFooterUI`** brackets the DECSTBM with cursor save/restore, so the cursor
stays where the last output left it:

```ts
process.stdout.write(
  saveCursorSequence() + setScrollRegionSequence(1, rows() - 2) + restoreCursorSequence(),
);
```

The other unprotected `setScrollRegion` calls (`teardownBottomUI`,
`resetSubmittedInputArea`, the resize handler) were deliberately left alone —
each is immediately followed by absolute positioning that masks the homing.

**`setupInputUI`** opens its 3 rows from wherever the cursor actually is:

```ts
writeChrome('\r\n\n\n');
```

Newlines scroll only once the cursor reaches the bottom margin, so this scrolls
by exactly what is needed: 3 when output fills the region (unchanged from
before), 0 on the startup screen. The `\r` drops an ONLCR assumption; column
drift would be harmless anyway since `drawInputArea` absolute-positions after.

**`writeChrome`, not `process.stdout.write`.** This is the subtlety that the
existing suite caught. `util/screen-buffer.ts` intercepts stdout and records
anything *without* a cursor/screen escape as transcript. The old write was
filtered out by its `\x1b[…H`; bare newlines are not, so they landed in the
buffer as three blank lines — which broke suggestion-overlay restore
(`tty-slash-backspace-restore` repainted blanks over the `/help` output) and made
`hasPostEpochContent()` report a transcript on a fresh screen, sending resize down
the reflow path instead of the banner-redraw path (`tty-resize-banner-narrow`,
`tty-resize-banner-widen`). `writeChrome` bypasses capture explicitly for writes
that are layout rather than output.

## Coverage

- `tests/e2e/tty-banner-not-scrolled.e2e.json` — asserts the compact banner's
  border string appears **twice** on the viewport. `screenContains` cannot catch
  this (the bottom border matches on its own); only the count distinguishes
  "banner intact" from "top border scrolled off". Pre-fix: `screen has 1×"…",
  expected 2`.
- `tests/cli/chrome/ansi.test.ts` — the extracted sequence builders, their
  writing forms, and the non-TTY geometry fallback.

## Also in this change

`bottom-ui.ts` crossed the 500-line limit, so the terminal geometry and escape
sequences it was built from moved to `src/cli/chrome/ansi.ts` (488 + 55). The new
module documents the DECSTBM cursor-homing behavior at its source, which is where
defect 1 would have been visible.
