# A delegated agent could approve its own work: `freecode checkpoint accept` from inside `shell_exec`

**Files:** `src/agent/tools/shell.ts`, `src/cli/checkpoint.ts`

`freecode -p --edit` runs an unattended agent with `create`/`edit`/`shell_exec`
and ask mode forced to `auto`. The whole safety story is the review gate: a
snapshot taken before the first write, a lock that keeps the project closed until
someone accepts or reverts, and `checkpoint diff` as the thing the reviewer reads.

One command from the agent's own shell removed all of it:

```
--- agent runs: freecode checkpoint accept ---
Accepted. <root> is the baseline as of snapshot 20260812T175106-199064.

review lock still held?      NO — released
reviewer now sees:           No changes since snapshot 20260812T175106-199064.
backdoor.js still on disk?   true
second `-p --edit` refused?  NO — allowed to start
```

Demonstrated end to end, not inferred
(`docs/scripts/containment-audit/selfapprove.mjs`). Every guarantee falls at
once, and the failure is silent in the worst direction: the reviewer is shown an
empty diff, which reads as "the agent changed nothing", while the payload sits on
disk and the project is open for the next delegation. `checkpoint revert` is the
same hole pointed the other way — it destroys the evidence before it is read,
plus any concurrent human edits in the tree.

**Cause:** freecode's control plane is a CLI on `$PATH`, and `shell_exec` is
`child_process.exec`. Nothing marked `checkpoint` as privileged, and nothing let
it tell the user's terminal from the shell of the run it was being asked to
approve. The `.git` block and the destructive-pattern list are regexes over the
command string; neither has any reason to match `freecode checkpoint accept`.

**Fix:** `shell_exec` stamps `FREECODE_SANDBOXED=1` on every child, and
`runCheckpoint` refuses `accept` and `revert` when it is set. Three details are
load-bearing:

- The refusal runs **before** `resolveSnapshotRoot`. `accept` snapshots first and
  releases the lock second, so a check placed inside `accept` would refuse *and*
  leave an agent-triggered baseline in `checkpoint list`.
- `list` and `diff` stay available. Reading is not approving, and an agent asked
  to describe its own change should be able to.
- The env is read per call, not captured at module load: `process.env` is still
  being written while `shell.ts` is imported.

**The trap this created**, since the marker is inherited: running `npm test`
*through* `shell_exec` — which `CLAUDE.md` actively encourages — would leak it
into vitest and every e2e child, failing every accept/revert case for a reason no
failure output would name. It is stripped in `vitest.config.ts`'s `env` and in
`STRIPPED_VARS` in `tests/harness/run-e2e.ts`. A green `npm test` from a plain
terminal cannot show this; both strips are deliberate, not tidying.

**What this is not.** An env marker is defeated by
`env -u FREECODE_SANDBOXED freecode checkpoint accept`, and it must be, because a
shell cannot be made to lie to its own child. This buys the time to build the
real fix — no `freecode` binary and no snapshot store inside the sandbox at all
(C1 in `docs/agent-containment-plan.md`). Anyone reading the refusal as
containment has the wrong model of it.
