# Tokenizer families silently stuck on fallback estimate (0-byte cache files)

**File:** `src/tokenizers/download-tokenizer.ts`

## Symptom

`.freecode/tokenizers/{llama-3,deepseek-v4}/tokenizer.json` were 0 bytes while
`glm-4` was a healthy 19MB. The exact-tokenizer registry reported those two
families as covered, but `countTokens` had been silently using the generic
o200k fallback estimate for them the whole time (`loadBpeJsonEncoder` throws on
the empty file → the throw is swallowed by `preloadTokenizerFor`'s try/catch).

## Root cause (two compounding bugs, plus a third found while verifying)

1. **`downloadFile` only followed 301/302 redirects.** HF's `resolve/main/<file>`
   endpoints redirect to a CDN, and the status code is *not stable across repos*:
   `GLM-4.5-Air` answered 302 (followed → downloaded fine), while
   `Meta-Llama-3-8B` and `DeepSeek-V4-Pro` answered **307**. A 307 fell through to
   the `!== 200` branch and rejected with "HTTP 307" — but `createWriteStream(dest)`
   had already truncated the file to 0 bytes, so an empty file was left on disk.
2. **`ensureTokenizerFile` treated any existing file as a cache hit** (`existsSync`),
   so the 0-byte leftover was never re-fetched. That is why the breakage was
   permanent and silent.
3. **HF's 307 `Location` is a *relative* path** (`/api/resolve-cache/...`).
   Even after adding 307 to the followed codes, `https.get(relativePath)` throws
   `ERR_INVALID_URL` *inside the response callback*, escaping the promise as an
   uncaught exception (and leaving a `.download` temp behind). Found only by
   driving the real network path, not by unit tests.

## Fix

- `downloadFile` follows the full redirect family (301/302/303/307/308), resolves
  relative `Location` headers with `new URL(location, currentUrl)`, wraps the
  response handler so any throw routes to a `fail()` path, and removes its
  partial output on any failure.
- `ensureTokenizerFile` treats an existing-but-empty file as absent
  (`statSync(dest).size > 0`), so broken caches self-heal on the next run. It
  now downloads to a sibling `<dest>.download` temp and promotes it via atomic
  `rename` only after a non-empty check — `dest` is therefore *only ever* a
  complete file, and a failed/empty download can never masquerade as a cache hit.

## Prevention

- The `size > 0` check (not a JSON parse — these files reach ~19MB) is cheap
  enough for the hot preload path and makes any future 0-byte corruption
  self-healing rather than permanent.
- Regression tests in `tests/tokenizers/download-tokenizer.test.ts` now cover the
  three failure paths that had zero coverage: a 0-byte cached file re-downloads;
  a download that resolves-but-writes-nothing returns null and leaves no dest
  file; a rejecting download leaves no dest file. The temp→rename seam is what
  makes these testable through the injected `downloadFn`.
- Verified end-to-end against live HF: the two 0-byte files repopulated
  (llama-3 → ~9MB, deepseek-v4 → ~6.3MB) and both families now produce exact
  counts that diverge from the fallback estimate. `npm test` does not exercise
  the real network, so that check must be done by hand (a one-off
  `preloadTokenizerFor` call per family).
