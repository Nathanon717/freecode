# 27-07-2026 — `tty-status-line-ticks` failed on Windows only: the fixture's tool slept with `sleep`, which cmd.exe does not have

## Symptom

`npm test` on Windows: 51 passed, 1 failed. The same commit was fully green on Linux.

```
FAIL  tty-status-line-ticks
        [submit - step 1's count is on screen while its tool is still running] screen missing: "1111 ctx"
        [submit - step 1's count is on screen while its tool is still running] screen unexpectedly contains: "5555 ctx"
        [submit - step 1's count is on screen while its tool is still running] screen unexpectedly contains: "Done waiting."
```

The three failures are one event: by the time the step asserted, the whole two-step turn had
already finished.

## Cause

The test proves the footer's ctx count updates *mid-turn* — it needs a window where turn 1's
usage (`1111`) is on screen while its tool is still running, before turn 2's usage (`5555`)
replaces it. The fixture bought that window with a slow tool call:

```json
{ "name": "shell_exec", "args": { "command": "sleep 4" } }
```

`shellTool` runs commands through `child_process.exec` (`src/agent/tools/shell.ts:41`), which
on Windows is `cmd.exe /d /s /c`. cmd.exe has no `sleep` — not a builtin, not on PATH:

```
'sleep' is not recognized as an internal or external command
```

`shellTool` catches the non-zero exit and returns the error as the tool result, so the tool
"succeeded" from the loop's point of view and returned in milliseconds. Turn 2 fired
immediately, the footer went straight to `5555 ctx`, and the mid-turn window the test exists
to observe was never on screen. Nothing about the status line was broken — the fixture's
timing assumption was Unix-only.

`sleep 4` was the only Unix-only command in any e2e fixture.

## Fix

The fixture now sleeps with node, which the harness already depends on:

```json
{ "name": "shell_exec", "args": { "command": "node -e \"setTimeout(()=>{},4000)\"" } }
```

A pending timer keeps the event loop alive for the full 4s, then the process exits 0 with no
output. Measured at 4.1s through both cmd.exe and `sh`. Under `sh -c` the double quotes keep
`()` and `{}` literal, so there is no brace expansion or subshell to worry about. Empty
stdout means the tool result still carries `<tool_result name="shell_exec">`, which turn 2's
`mustContain` matches — unchanged on both platforms.

The `.e2e.json` description now records why the command is not `sleep`, since JSON has no
comments and the obvious "simplification" reintroduces the bug.

## Coverage

The test is its own regression test: it fails on Windows with `sleep` and passes with
`node -e`. Verified by running it on Windows before and after, then the full e2e suite
(52 passed).

## Still open

Unrelated, and not a failure — the run prints a swallowed cleanup error on Windows:

```
[cleanup] failed to remove tmpStore: Error: EPERM ... freecode-store-blocklist-purge-script-mode-...
```

Something still holds a handle on that store — likely the child's SQLite file, though that
was inferred from the directory name, not confirmed — by the time `run-e2e.ts:331` calls
`rmSync`, so the temp store leaks. Reproduced on three consecutive runs. It is logged, not asserted, so the
suite is green. The usual remedy is `maxRetries`/`retryDelay` on the harness's `rmSync`
calls; left alone here because a single clean run cannot distinguish a working retry from a
handle that happened to be free.
