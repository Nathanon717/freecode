# `git config core.hooksPath` was RCE that survived `checkpoint revert` and never showed in the diff

**Files:** `src/snapshots/gitdir.ts` (new), `src/snapshots/index.ts`,
`src/snapshots/coverage.ts`, `src/snapshots/shadow-repo.ts`, `src/cli/checkpoint.ts`

`.git` was outside snapshot coverage entirely, so everything in it was whatever the
agent left. `core.hooksPath` points git at a hook directory of the agent's choosing;
the next `git commit` the user runs executes it. Demonstrated
(`docs/scripts/containment-audit/snaptest.mjs`):

```
hooksPath in diff?         false
evil hooksPath cleared?    false   (after revert)
hook actually executed?    yes
deleted branch recovered?  false
```

The first run of that script proved the point more vividly than intended, with a
`curl` hook resolving a hostname during a test `git commit`.

Branch deletion was the same hole pointed at history: `git branch -D` followed by
`reflog expire --all --expire=now && gc --prune=now` put the commits beyond any
recovery a worktree snapshot could offer. None of it contains the string `.git`, so
no guard in `git-guard.ts` matched any of it.

**Why it could not be a wider `git add`.** Both obvious approaches are refused by
git, and both were checked rather than assumed: `add -f -- . .git` stages nothing,
because git skips any directory named `.git` during the worktree walk and `-f`
overrides *exclude files*, a different mechanism; and the tree cannot be grafted in
afterwards either, because `read-tree --prefix=.git/` fails with
`invalid path '.git/config'` — `verify_path` refuses index entries under a `.git`
component precisely so a hostile tree cannot write one.

**Fix:** capture `.git` as a **second work tree** — the same shadow repo driven with
`--work-tree=<project>/.git`, giving a tree whose paths are relative to `.git`
itself. Its commit is recorded as the **parent** of the snapshot commit, so the ref
already protecting the snapshot protects it too and `pruneSnapshots` needs no second
namespace. Restore is the same `add` + `read-tree -u --reset` pair rooted at `.git`,
run *after* the worktree, since `.git` holds the index describing it.

That collapses three mechanisms into one. The byte-copy of `.git/index` and its
`indexCopyPath` are gone — the index is in the tree now — and `restoreHead` stops
being the rollback path, staying only for the cases with no `.git` commit to
restore: a pre-R3 snapshot, a `.git` that is a *file* (linked worktree, whose real
git dir is outside the project and deliberately skipped), and a `.git` restore that
failed. A `.git` the agent deleted outright is now rebuilt, where the old code
printed a warning saying history was gone for good.

`checkpoint diff` gained a `.git` section, restricted to `config` and `hooks/` and
always raw in both modes — that is the RCE surface, and `core.hooksPath` pointing
somewhere new means nothing summarised. Refs, logs and objects stay out because they
churn on every git command an agent runs. The trade is explicit: a deleted branch is
*recovered* by a revert without being *shown* by the diff.

**A locked file inside `.git` is worse than one in the worktree, and the two failure
shapes differ.** Holding a file open the way SQLite does (no share-delete), the same
shape that forced `.freecode` out of coverage in [12-08-2026f.md](12-08-2026f.md):

| git must | Result |
| --- | --- |
| **delete** a file it cannot (a packfile) | `warning:`, exit 0, restore completes |
| **replace** a file it cannot (`.git/index`) | `error:`, exit 128, restore aborts mid-write |

The second left refs rolled back against a stale index, with `git fsck` reporting a
broken cache-tree — neither the snapshot nor what the agent produced. The worktree
half's treatment ([13-08-2026c.md](13-08-2026c.md): name the paths, since git restored
everything else) cannot be borrowed, because "everything except `refs/heads/main`" is
not a description of a git directory. What saves it is that
`read-tree -u --reset` is idempotent: re-running the revert once the holder lets go
was verified to repair the state completely, `fsck` clean and the staged/unstaged
split intact. So the failure is caught, the worktree restore is kept, `restoreHead`
is still attempted, and the warning says to run the same revert again — as a
**failed** revert: exit 1, and the review lock stays held. Caught in review, where
the first cut warned and then released the lock and returned 0, which would have
marked a broken `.git` reviewed, admitted the next delegated run against it, and
removed the outstanding lock that keeps a repeated revert aimed at that snapshot.

`checkpoint list` had the same false line one function above the one this fixed: it
printed "(no changes since this snapshot)" for a `.git`-only change, which is the
finding's exact signature — a `core.hooksPath` edit leaves the worktree spotless. It
now flags the snapshot and points at `diff` rather than growing a stat of its own.

**Cost:** +12s cold and +0.1s warm per snapshot on this repo (~3600 files in a 19 MB
`.git`), taking a project's first snapshot to ~24s and every one after to ~0.4s.
Paid once per project. Packfiles dedupe by content hash, so later snapshots store
only what changed. The e2e harness needed no change — it pre-warms by taking one
real snapshot, which warms both walks.

**Not closed by this.** A planted hook is now *reversible*, not *harmless*: it still
executes during the agent's own session, so the `git-guard.ts` regexes stay until
containment lands (C5 in `docs/agent-containment-plan.md`). And
`git config --global core.hooksPath` writes outside the project, where no project
snapshot reaches — that half of the finding waits on C4's environment scrub.
