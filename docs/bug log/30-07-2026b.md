# 30-07-2026b — Read-only sessions were told they could edit files (and `TRANSCRIPT_STREAM=null` never silenced model text)

## Symptom

Found while building `freecode -p`, whose whole point is a read-only turn. Asked a
`-p` run to list the tools it had:

```
$ freecode -p "List the tool names you have available, one per line, then stop."
read
create
edit
grep
shell_exec
spawn_agent
list_dir
```

Only three of those existed. `createTools(..., readOnly)` returns
`read`/`grep`/`list_dir`, but `buildSystemPrompt` hardcoded the full list:

```ts
Available tools: read, create, edit, grep, shell_exec, list_dir${spawnAgent ? ', spawn_agent' : ''}
```

plus the rules that go with them — "Before editing a file, read it with read
first…", and the tip about running broken code to see the error, in a session with
no `shell_exec`.

## Why it matters

Not cosmetic. The model believes the prompt over the tool schema: it plans an edit,
calls `edit`, gets "no such tool" back, and burns steps recovering. This predates
`-p` — the Ctrl+R read-only toggle has always had it — but `-p` is read-only for its
entire life, so it goes from an occasional annoyance to the default experience.

## Cause

`spawnAgent` was the *only* conditional in the prompt's tool list, added by
[25-07-2026d.md](25-07-2026d.md) for exactly this class of bug: the prompt advertised
`spawn_agent` where `runParsedToolsLoop` had not created it. That fix was a
single boolean for the single tool that was wrong at the time. `readOnly` reaches
`createTools` through the very same options object and was never given the same
treatment, so the second way to desynchronise the prompt from the tool set stayed
open.

## Fix

`buildSystemPrompt` takes `toolNames` — the actual list — instead of a per-tool flag,
and `agent/tools/tool-names.ts` exports `offeredToolNames({ readOnly, spawnAgent })`
so the prompt and `createTools` are driven from one place. The prompt derives three
things from it: the `Available tools:` line, the editing rules (replaced by a
"this session is read-only" statement when the set has no write tool), and the tips
(each tip belongs to a tool and is dropped with it).

A parametrised test asserts `offeredToolNames` equals `Object.keys(createTools(...))`
for all four flag combinations, so the two cannot drift again — that is what was
missing after 25-07-2026d, which fixed the instance rather than the class.

The same commit drops `spawn_agent` from read-only mode. A sub-agent is itself
read-only, but a call spends a whole LLM sub-turn, which is more than reading.

## Secondary: `null` was not silent

`writeTranscriptText` wrote straight to `process.stdout`, bypassing the transcript
stream — a leftover from when the stream defaulted to stderr and model text had to
escape it. So `FREECODE_TRANSCRIPT_STREAM=null` silenced tool chrome but not the
model's own text: unit tests have been printing response text all along (two of them
depended on it), and `-p` printed its answer twice, once streamed and once from
`result.text`. Now it goes through the stream like every other transcript write. Two
tests that assert on visible output opt out of the suite-wide `null` with
`vi.stubEnv`.
