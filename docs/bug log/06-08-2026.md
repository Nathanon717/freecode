# 06-08-2026 — Zen turns died with "The `reasoning_content` in the thinking mode must be passed back to the API"

## Symptom

Reported against `zen:deepseek-v4-flash-free` and `zen:big-pickle`, intermittently:

```
Error: OpenCode HTTP 400 Bad Request: Error from provider (Console): Upstream
request failed: [invalid_request_error] The `reasoning_content` in the thinking
mode must be passed back to the API. (code: invalid_request_error)
```

The turn had already made tool calls (`toolCalls=3`), so the work was done and
thrown away — the 400 lands on a *continuation* request, never on the first one.

## Cause

DeepSeek's API rejects an assistant message that carries `tool_calls` but no
`reasoning_content` field. The AI SDK 3.4 `@ai-sdk/openai` client predates
reasoning support: it drops `reasoning_content` deltas while parsing the response
stream, so the field is gone from `responseMessages` before anything in freecode
could see it, and every continuation request re-sends a `tool_calls` message
without it.

Why it looked flaky: zen load-balances each request between two upstreams,
distinguishable by response id.

- `id: "router-…"` — does not enforce the rule.
- `id: "<uuid>"` (the "Console" backend in the error text) — enforces it.

`deepseek-v4-flash-free` gets routed to either, so it fails at whatever rate the
router happens to pick Console — 1/8 in one measured session, 5/12 when the same
captured body was replayed. `big-pickle` pins to Console and fails **8/8**. That
is the deterministic repro: replay any continuation request under `big-pickle`.

Bounds, all measured by replaying one fixed body:

- Only assistant messages with `tool_calls` are checked; a text-only assistant
  message passes without the field (0/8 failures).
- The check is on **presence**, not content: `reasoning_content: ""` passes 5/5,
  and so does a string that has nothing to do with what the model thought.
- Only the last such message is required to have it, but attaching it to all of
  them is accepted too (5/5).
- The other zen models tolerate the extra field and ignore it (`mimo-v2.5-free`,
  `nemotron-3-ultra-free`, `north-mini-code-free`, 3/3 each).

## Fix

`ensureAssistantReasoningContent` in `providers/adapters/openai-compat-request.ts`
adds `reasoning_content: ''` to every assistant message that carries `tool_calls`
and does not already have the field, wired in as the `zen` entry in
`providerQuirks`. Since the check is presence-only, there is nothing to recover
and no state to keep — no response-side capture, no `toolCallId → text` map, and
so nothing that could go wrong across sub-agents or process restarts.

It sits in the request-body transform inside `customFetch`, which is the last
thing to touch the body before it leaves, so it covers any history the SDK
serializes, not just the shape `agent/turn-messages.ts` produces.

## Verification

- `big-pickle`, the 8/8 failure case: 3/3 clean `-p` turns after the fix.
- `deepseek-v4-flash-free`: 5/5 clean.
- Unit coverage on the pure transform in
  `tests/providers/adapters/openai-compat-request.test.ts`.
