# Turso still not enabled outside the repo root — the real cause was in `src/index.ts`, not the launch wrapper

**Files:** `src/index.ts`, `docs/device-setup.md`, `docs/map/index.md`

Same symptom as [18-07-2026c.md](18-07-2026c.md) — `/status` shows Turso configured
when freecode is launched from the repo root and "not configured" everywhere else.
That entry concluded the fault was two independent launch-wrapper issues and that
"nothing in `src/` reads `process.cwd()` for store or config resolution" — true for
`store-paths.ts`, but incomplete: it missed a second, in-source Doppler path.

**Actual cause:** `tryInjectDoppler()` in `src/index.ts` (added in `fc500f8`,
2026-06-19) runs on every launch and self-injects secrets by shelling out to
`doppler secrets download --format=json --no-file` — with no `--project`/`--config`
flags. Like `doppler run`, an unpinned `doppler secrets` call resolves its project
from the **current directory** via the scope table in `~/.doppler/.doppler.yaml`.
The scope was only ever registered on the repo path, so the call silently
succeeded there and silently failed (`result.status !== 0`, swallowed on purpose)
everywhere else — with no shell wrapper involved at all. Confirmed directly:
`doppler secrets download` unpinned returns full JSON from the repo root and
`You must specify a project` from `C:\`; pinning `--project freecode --config dev`
succeeds from both.

This also explains why the 18-07 fix never actually landed on this machine —
there was no shell wrapper anywhere to install it into (no `~/.doppler` PATH shim,
no shell rc function, no PowerShell profile, no `cmd.exe` `AutoRun`, no VS Code
workspace env, no Windows Terminal profile). The app didn't need one; it was
already doing this itself, just with the same unpinned-cwd bug baked in.

**Fix:** pinned the `spawnSync` args to
`['secrets', 'download', '--project', 'freecode', '--config', 'dev', '--format=json', '--no-file']`.
Verified by running the built `dist/index.js` with cwd `C:\` (outside the repo)
in scripted mode — `/status` now reports `Turso sync: configured` and
`Doppler: active (project: freecode / dev)`.

**Doc fix:** `docs/device-setup.md`'s "Add the shell wrapper" step is now
unnecessary for Doppler injection specifically — the app self-injects on every
launch, pinned, so plain `freecode` from any directory works once `doppler login`
has run. Left the wrapper documented since it still applies to `pty`/`test-all-models`
diagnostics run via `npx tsx` and to explicit `FREECODE_HOME`/other non-Doppler
env overrides, but reframed the failure-mode section around this real cause
instead of the wrapper.

**Follow-up (not done):** `tryInjectDoppler`'s injected secrets never include
`DOPPLER_PROJECT`/`DOPPLER_CONFIG` unless Doppler exposes them as computed
secrets in that config (it does here) — worth confirming this holds generally
before relying on `/status`'s "Doppler: active" line as a self-injection signal.
