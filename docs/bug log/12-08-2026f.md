# Gitignored files were invisible to `checkpoint diff` and survived `checkpoint revert`

**Files:** `src/snapshots/index.ts`, `src/snapshots/shadow-repo.ts`, `src/cli/checkpoint.ts`

`git --git-dir=<shadow> --work-tree=<project> add -A` honours the project's
`.gitignore`, so anything ignored was outside the snapshot in **both** directions.
Demonstrated (`docs/scripts/containment-audit/snaptest.mjs`) with a stock
`.gitignore` of `node_modules/`, `dist/`, `.env`:

```
payload mentioned in diff?   false
.env deletion in diff?       false

after checkpoint revert:
  dist/payload2 gone?        false     <- still there
  .env recovered?            false     <- gone for good
```

Two failures, pointing opposite ways. A delegated agent could hide a payload where
the reviewer's diff would never show it — `dist/` or `node_modules/.bin/` needs no
`.gitignore` edit in any normal JS project — and it also meant an agent that
deleted an ignored `.env` or a local SQLite DB had destroyed it permanently, since
a snapshot that never captured a file cannot put it back.

The revert output made this worse rather than better: it printed a one-line note
that files ignored by `.gitignore` "were left as they are" whenever the project had
a `.gitignore` at all. Technically true, and useless — it never said *which* paths
were outside coverage, so a reviewer could not tell an absent `node_modules` from
one full of payloads.

**Fix:** all three staging calls — `takeSnapshot`, `snapshotDiff`,
`restoreSnapshot` — now come from one builder, `stagingArgs()`, which adds `-f`.
The single builder is the point: restore's `read-tree` deletes by diffing *its*
index against the snapshot tree, so a restore staging less than the snapshot
captured would leave behind exactly what the diff had just shown.

`node_modules` is excluded at any depth by pathspec (`:(exclude,glob)**/node_modules/**`),
by prevention rather than backup — containment mounts it read-only, and it is
316 MB here against 4 MB for everything else ignored. `FREECODE_SNAPSHOT_EXCLUDE`
replaces the list. Revert now enumerates the excluded paths that really exist
instead of printing the old note.

**Removed in the same change:** the shadow repo's `info/exclude`, which held
`/.git/`. `-f` overrides `info/exclude` exactly as it overrides `.gitignore`
(verified both ways), so it was a guard that did nothing. What actually keeps the
project's `.git` out of a snapshot is git skipping any directory of that name
during the worktree walk — which is why snapshotting `.git` needs its own
mechanism, not a looser add.

**Cost, measured before and after on this repo:** first snapshot in a project
3.0s → 11.8s, every snapshot after 0.20s → 0.29s, store 1.8 MB → 4.3 MB. The cold
number is file count, not bytes. It broke two TTY e2e scenarios by blowing a
`waitFor` budget from inside the snapshot gate; the harness now pre-warms the
shared snapshot store once before the run, which is what its shared
`FREECODE_SNAPSHOT_DIR` was always for.

**A second defect this created, caught before shipping.** A revert now deletes and
restores ignored files, which put freecode's own `.freecode/` store — live SQLite,
`-wal`, `-shm` — inside the blast radius wherever freecode runs from source. Tested
with a live libsql connection, `read-tree -u --reset` **threw**: git cannot rewrite
files the running process holds open on Windows, and it fails part-way through, so
`checkpoint revert` was broken in this repo's own dev setup. `.freecode` is now in
the default exclusion list, and the same test restores cleanly with the database
passing `PRAGMA integrity_check`.

That fixes the case that can be named. Any *other* live database inside coverage — a
user's `dev.db` held open by their dev server — still aborts a revert the same way,
and no exclusion list can enumerate those; the fix is for restore to skip what it
cannot write and say so, filed as R5 in `docs/agent-containment-plan.md`.

**Also not fixed here:** ignored files' contents now enter a shadow repo that never
runs `git gc`, so a `.env` captured once persists there in plaintext (C13 in the
audit, which this makes materially worse).
