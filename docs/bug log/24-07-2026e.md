# `npm test` crashed ~50% of runs with "Projects have different 'maxWorkers'", but never standalone

**Files:** `vitest.config.ts`

Roughly half of `npm test` runs died before a single test executed:

```
Error: Projects "" and "" have different 'maxWorkers' but same 'sequence.groupOrder'.
Provide unique 'sequence.groupOrder' for them.
 ❯ groupSpecs node_modules/vitest/dist/chunks/cli-api.BK8pd4xc.js:3808:8
```

It vanished on retry and never appeared when the same unit command was run on
its own, so it read as generic vitest 4.x flakiness. The message is also
actively misleading: it names *projects*, and this repo configures exactly one.
Both names print empty — the single default project disagreeing with itself.

**Cause:** vitest 4 resolves the worker count **once per test file**, while
grouping specs (`cli-api` `resolveMaxWorkers`, called from `groupSpecs` per
spec):

```js
function resolveMaxWorkers(project) {
  if (project.config.maxWorkers) return project.config.maxWorkers;
  if (project.vitest.config.maxWorkers) return project.vitest.config.maxWorkers;
  const numCpus = os.availableParallelism();   // re-read for EVERY spec
  return Math.max(numCpus - 1, 1);
}
```

`vitest.config.ts` set no `maxWorkers`, so both short-circuits were falsy and
each of the 111 spec files independently asked the OS for the CPU count.
`groupSpecs` throws the moment two specs in one group disagree.

The dev box is an Android phone under PRoot (`/sys/devices/system/cpu/core_ctl_isolated`
— Qualcomm core control), where the kernel isolates CPU cores under thermal and
foreground-app load. The reported crashes happened while a game was running. A
core dropping out mid-grouping makes file N resolve 7 workers and file N+1
resolve 6. Idle, the count is stable — sampling `availableParallelism()` in a
tight loop never varied from 8 — which is why standalone runs looked clean and
the failure looked like a coin flip. (That loop spans microseconds, so it shows
the count is steady at an instant, not across a 70-second run; the run-scale
evidence is the soak below.)

**Reproduced deterministically** rather than waited for: a `--require` shim in
the parent process (`groupSpecs` runs in the main vitest process, not a worker)
that makes `os.availableParallelism()` alternate `8, 7, 8, 7…` reproduces the
error verbatim, on demand, every run.

**Fix:** sample the CPU count once at config load and pin it, using vitest's own
default formula so the worker count is unchanged:

```ts
const maxWorkers = Math.max((os.availableParallelism?.() ?? os.cpus().length) - 1, 1);
```

This populates `project.config.maxWorkers`, so `resolveMaxWorkers` short-circuits
on its first line and can never observe a changing CPU count mid-run.

Tradeoff: the pinned value is a snapshot taken at config load. If the machine is
throttled at that instant the whole run uses a lower worker count — slower, but
never a crash. Noted in the config comment so the number isn't mistaken for a
live reading.

**Verification:**

- The adversarial shim that crashed the suite deterministically before the fix
  now runs clean: 111 files, 2066 tests passed.
- 7 consecutive full unit runs under 3 CPU spinners (contention mimicking the
  loaded-phone conditions), alternating shim-on/shim-off — all green. (The soak
  was scripted for 20 and stopped early at 7 by request; 7 is what was observed.)
- Full `npm test` green end to end.
- All four vitest invocation paths re-checked under the shim — the pipeline unit
  run, `time.ts`'s `--reporter=json`, a foreign cwd via `--root`, and `pty:test`.
  A control run pinned to a copy of the pre-fix config crashes on as few as 3
  spec files, so those passes are sensitive, not vacuous.

**Checked and deliberately not changed:** `tests/harness/run-e2e.ts` also reads
`availableParallelism()`, but in a module-level one-shot IIFE that computes
`E2E_CONCURRENCY` a single time. Same class of input, no drift hazard.
