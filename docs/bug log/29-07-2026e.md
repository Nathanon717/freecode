# 29-07-2026e — e2e TTY segfault: mid-run, inside node-pty's ConPTY path

> **Superseded by [29-07-2026f.md](29-07-2026f.md), which fixes this.** The
> diagnosis below (mid-run, inside `useConptyDll`) holds and the measurements
> stand, but two conclusions are wrong: version pinning is *not* closed, and the
> resize regression is not node-pty's code. One package ships two independently
> versioned components with one defect in each — a data race on node-pty's global
> pty table (fixed in beta.13) and the vendored ConPTY host's resize delivery
> (regressed in 1.25, pinned back to 1.23). See f before acting on anything here,
> especially the containment proposal under "Still open".

## Symptom

`npm test` / `npm run test:e2e` die with a segfault (exit 139 from Git Bash, exit
`3221225477` = `0xC0000005`, an access violation, from `test.ts`). No `FAIL`, no
assertion output, no partial results — a silent kill, not a test failure. A clean
run's log is also just the npm banner, so log size never distinguished the two;
only the exit code does.

## What this entry corrects

The "Still open" note in [29-07-2026d.md](29-07-2026d.md) recorded this as a
teardown-at-exit bug: `run-e2e.ts` ending on `process.exit()` while ConPTY
teardown was in flight. **That premise is wrong.** Instrumenting the harness with
a per-scenario progress line showed the crash landing *mid-run*, long before the
exit path: runs died after 4, 4, 10 and 17 of 39 TTY scenarios, and one died 7s
into a 37s run. On a crashing run the final `process.exit()` is never reached.

## Root cause

Inside node-pty 1.1.0's `useConptyDll` path — not in this repo. Two independent
ways of leaving that code path take the crash to zero, and each breaks scenarios
for an unrelated reason:

| lever | segfaults | breaks |
| --- | --- | --- |
| baseline | 4/6 (`--only-tty`, instrumented) | — |
| deterministic teardown (below) | 2/14 | nothing |
| `E2E_CONCURRENCY` 6 / 4 / 2 | 1/8 · 2/12 · 0/4 | wall time only |
| `useConptyDll: false` | 0/6 | `tty-blocklist-purge` hangs at the confirm prompt — *not* because Enter is undelivered; see [f](29-07-2026f.md) |
| node-pty 1.2.0-beta.14 | 0/8 | 3–4 resize scenarios fail whenever other ptys are live |

Capping concurrency is **not** a mitigation — the rate is flat across 8/6/4 once
the samples are pooled. An early 0/6 at 4 looked like a trend and regressed to
2/6 on the next batch; don't re-run this.

The beta is not a misconfiguration on our side: its `WindowsTerminal` drops the
`useConpty` parameter but still maps `opt.useConptyDll` to the right slot. Its
resize regression is real, appears only with several pseudoconsoles live (the
same scenarios pass in isolation), and got *worse* at lower concurrency — so it
is not a settle-window problem, and tuning `quietMs` to accommodate a beta
dependency was rejected.

> Corrected in [29-07-2026f.md](29-07-2026f.md): the resize regression is not in
> node-pty's code at all — beta.11 and beta.12 ship byte-identical `lib/`, and
> the regression tracks the vendored ConPTY host bump, which delivers a resize to
> the child ~70× slower (15ms → ~1-1.5s) and sometimes not at all. Rejecting a
> `quietMs` bump was right, and for a stronger reason than stated: no wait can
> cover a notification that never arrives.

### No version pin resolves it — WRONG, see [29-07-2026f.md](29-07-2026f.md)

The sweep below is accurate. The inference from it is not: the crash fix and the
resize regression live in two *different* components that happen to ship
together. No single version has both because the vendored ConPTY host regressed
one release before the crash was fixed — so the fix is beta.14 (crash) with the
host pinned back to 1.23 (resize), which no version can express on its own.

All fourteen 1.2.0 betas were swept (`--only-tty`, one run each; then 10 runs on
the candidate). The crash fix and the resize regression arrive together:

| betas | resize | segfault |
| --- | --- | --- |
| 1–5 | clean | not exercised enough to say |
| 6–9 | clean | **crashes** (1/1 each) |
| 10–11 | clean | **crashes** (beta.11: 3/10) |
| 12 | 1 scenario fails | — |
| 13 | 3 scenarios fail | — |
| 14 | 3–4 scenarios fail | 0/8 |

beta.11 is the newest build with working resize and it still crashes 3/10; the
first build that stops crashing (14) is past the regression. **There is no version
of node-pty that has both.** Pinning is closed as an avenue — don't re-sweep this.

## What did get fixed: the PTY leak

`driver.ts`'s `kill()` skipped `proc.kill()` entirely when the child had already
exited, which is the normal case — a TTY scenario ends by sending Ctrl-C. node-pty
releases the ConPTY and its conout worker **only** from `kill()`, and on the
`useConptyDll` path it defers the worker disposal to an `_outSocket.on('data')`
callback that a dead child never fires. So every scenario left a worker thread
and a pseudoconsole alive for the rest of the run.

Measured directly: at the end of `--only-tty`, **39 of 39** conout workers were
undisposed, with 39 `MessagePort`/`PipeWrap` pairs still in
`process.getActiveResourcesInfo()`.

`kill()` is now unconditional and idempotent: it kills the proc, reaches in to
dispose the conout worker (the only way to release that thread deterministically),
and disposes the xterm `Terminal`. `onData` drops late data so a post-teardown
write can't hit a disposed emulator.

This is a leak fix, not a crash fix. It may reduce crash frequency — 2/14 against
a 2/6 stated baseline — but the difference is inside the noise for these sample
sizes, and the full suite still crashed 3 of 4 `npm test` runs afterwards. It is
kept because releasing what you allocated is correct on its own merits, and
because it makes `driver.test.ts`'s "second kill is safe after process already
exited" actually exercise the kill path instead of a no-op.

## Do not redo

- **Synthetic repros do not reproduce it.** Three scripts, ~25 runs: N up to 60
  ptys, heavy continuous child output, a mix of exited and still-running children
  at teardown, xterm in the data path, and forced `gc()` between batches to test
  whether GC of an unkilled `IPty` finalizes native handles under a live worker.
  Zero crashes. Only the real concurrent suite reproduces.
- **A single scenario in a tight loop** (`--only=<name>`, 20×) never reproduces.
- Node's `--report-on-fatalerror` produces no report for this crash; it is a
  native access violation, not a V8 fatal error.

## Not the blocklist-purge feature

Worth stating because the two got conflated — the EPERM bug in
[29-07-2026d.md](29-07-2026d.md) *was* blocklist-specific (those are the only two
scenarios calling `seedModels`). This one is not. With
`tty-blocklist-purge.e2e.json` deleted outright, `--only-tty` still segfaulted
**4/8**. Any 38 TTY scenarios reproduce it; removing the feature buys nothing.

## Still open

> **Nothing. Fixed in [29-07-2026f.md](29-07-2026f.md).** The containment plan
> below was never built and should not be: the crash has a cure. Kept only as the
> record of what the dead end looked like from inside.

The segfault itself. `--skip-tty` remains clean, so the non-TTY e2e path is
unaffected.

With upstream pinning closed (above), the remaining approach is harness
containment rather than a cure — the e2e setup turns a recoverable dependency
crash into a total loss:

1. All 39 TTY scenarios share one process, so a native crash destroys every
   result. No `FAIL`, no partial output, and `test.ts` then halts the pipeline so
   the unit tests never run either.
2. A crash and a pass produce the same log (just the npm banner) — only the exit
   code differs. That is how this stayed opaque for weeks.

The proposal: shard the TTY phase across child processes and retry a shard that
dies on a signal, so one upstream crash costs one shard instead of the run, and
emit a per-scenario progress line. Rough arithmetic — crash rate scales with pty
spawns per process, so ~10 scenarios a shard puts each at roughly 7%, and one
retry per shard takes a run to ~1-2%. It is containment, not a fix; the crash is
still there and this entry stays open until node-pty ships both halves.
