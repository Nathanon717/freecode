# 29-07-2026e — e2e TTY segfault, cured: a data race in node-pty, and a ConPTY host pinned back

## Symptom

`npm test` / `npm run test:e2e` died with a segfault (exit 139 from Git Bash, exit
`3221225477` = `0xC0000005`, an access violation, from `test.ts`). No `FAIL`, no
assertion output, no partial results — a silent kill, not a test failure. A clean
run's log is also just the npm banner, so log size never distinguished the two;
only the exit code does.

Cured. Two changes, one per defect:

- node-pty `1.1.0` → `1.2.0-beta.14`, for the segfault.
- the ConPTY *host* pinned back to 1.23.251008001, for resize delivery.

**Verified: 35/35 `--only-tty` runs and 10/10 full `npm test` runs clean.** The
old pin segfaulted 2/5 on the same box the same day.

## What this entry corrects

The "Still open" note in [29-07-2026d.md](29-07-2026d.md) recorded this as a
teardown-at-exit bug: `run-e2e.ts` ending on `process.exit()` while ConPTY
teardown was in flight. **That premise is wrong.** Instrumenting the harness with
a per-scenario progress line showed the crash landing *mid-run*, long before the
exit path: runs died after 4, 4, 10 and 17 of 39 TTY scenarios, and one died 7s
into a 37s run. On a crashing run the final `process.exit()` is never reached.

The first diagnosis written here then concluded that no node-pty version had both
a crash fix and working resize, and closed version pinning as an avenue. The
measurements behind that were sound; the conclusion was not — see
[The dead end: "no version has both"](#the-dead-end-no-version-has-both) below,
kept because its negatives are still load-bearing.

One npm package ships **two independently versioned components**, and there is one
defect in each — so the answer was never a version, it was a version *plus* a host
pin:

| component | defect | resolution |
| --- | --- | --- |
| `conpty.node` (node-pty's C++) | data race on the global pty table → access violation | fixed upstream in **beta.13** |
| `third_party/conpty` (Microsoft's ConPTY host) | resize delivery 15ms → ~1-1.5s, unreliable under load | pinned back to **1.23** |

## Root cause 1: an unsynchronised `std::vector` in conpty.cc

node-pty keeps every pseudoconsole in one file-scope
`std::vector<std::unique_ptr<pty_baton>> ptyHandles`. Before beta.13 it was
touched from two threads with no synchronisation:

- the **JS thread** appends in `startProcess`, and takes raw `pty_baton*` out of
  it via `get_pty_baton` in `connect`, `resize`, `clear` and `kill`;
- the **exit-callback thread** erases from it in `remove_pty_baton` when a child
  exits.

An erase frees the `unique_ptr`'s baton and can reallocate the vector's buffer
while another thread is holding or about to dereference a pointer into it —
a use-after-free, which is exactly `0xC0000005`. beta.13 wraps every access in a
`g_ptyHandlesMutex` (and makes the id counter `std::atomic`).

This explains every negative in the "do not redo" list below. The race needs one
pty exiting while another is spawned, resized or killed, so it reproduces only
with many scenarios in flight — never a single scenario in a loop, and not in
synthetic repros that spawned ptys without that interleaving. It also explains
why the crash landed mid-run rather than at teardown.

Crash rate tracks the mutex and nothing else — note the two rows with the *same*
DLL and different node-pty, and the two with the same node-pty and different DLL:

| node-pty | mutex | ConPTY | segfaults |
| --- | --- | --- | --- |
| 1.1.0 | no | 1.23 | 2/5 |
| beta.11 | no | 1.23 | 3/10 |
| 1.1.0 | no | 1.25 | 4/10 |
| beta.14 | **yes** | 1.25 | 0/15 |
| beta.14 | **yes** | 1.23 | **0/35** |

Note what is *not* the fix: beta.11's deferred `connect()` (their #763, "to avoid
blocking the Node.js event loop in `ConnectNamedPipe`") is a real fix for a
different problem, and beta.11 still crashed 3/10.

## Root cause 2: ConPTY 1.25 resize delivery

node-pty >= beta.12 vendors ConPTY 1.25.260303002 in place of 1.23.251008001.
Time from `pty.resize()` to the child's `process.stdout` `'resize'`, same
node-pty, only the host swapped:

| ConPTY | latency |
| --- | --- |
| 1.23.251008001 | 15ms, 15ms, 15ms |
| 1.25.260303002 | 1041ms, 1557ms |

Worse than slow, it is unreliable: with a 10s wait budget, `tty-resize-*` still
failed 3/8 full runs, and `TTY_DUMP` showed why — the app was still painted at
**80 columns** after being resized to 60, i.e. it had never been told at all. No
harness wait can cover that, which is why the host is pinned rather than waited
on. (Rejecting a `quietMs` bump was right from the start, and for a stronger
reason than the one first recorded: no wait can cover a notification that never
arrives.)

`scripts/install/pin-conpty.cjs` (wired into `postinstall`) copies 1.23 over
node-pty's bundled host. The files come from a `conpty-pinned` devDependency —
an alias for `node-pty@1.1.0`, which shipped 1.23 — so no binaries live in this
repo. The host is a plain pair of files loaded by path: `LoadConptyDll` in
`conpty.cc` resolves `conpty\conpty.dll` relative to the **loaded**
`conpty.node`, which is `prebuilds/win32-<arch>/` on a prebuilt install
(`build/Release/` holds a copy but no `.node`, so it is never the one in play).
The script writes both and drops a `.pinned-<version>` marker; `run-e2e.ts`
warns if the marker is gone, so a reinstall that skips our postinstall can't
quietly restore the flakiness.

Two alternatives were measured and rejected. Vendoring the two 1.23 files
directly (~1.2 MB of Microsoft binaries in git) works but is the more invasive
choice. `useConptyDll: false` — which loads the OS's own ConPTY from kernel32,
where resize delivery is ~16-31ms — passes 38 of 39 scenarios but fails
`tty-blocklist-purge` 7/7 at its confirm prompt. That was first attributed to
Enter never being delivered; **that is a misdiagnosis** — a probe shows the child
does receive `"\r"` on that path. The real cause is unknown and wasn't pursued,
since the path isn't needed.

## The harness bug this exposed

`driver.waitQuiet()` returns immediately when the stream has *already* been quiet
for `quietMs`, so "the app has not been told to redraw yet" and "the app has
finished redrawing" are indistinguishable to it. At 15ms of resize latency that
never mattered; at 1.5s it was asserting against a screen the app had not been
asked to repaint. `run-tty-e2e.ts` now waits for a step's `screenContains`
needles on the rendered viewport — the same surface the assertions read — before
settling, and evaluates absences and counts only once the positives land
(`tty-resize-banner-widen`'s "no leftover compact banner" is a *pre-redraw* state
that resolves when the redraw arrives). A step already in its expected state pays
one poll.

To be clear about credit: this did **not** fix the resize scenarios — the host
pin did. It closes a genuine hole that was latent since those scenarios were
written, and it is why a late redraw now fails loudly instead of racing.

Two cheaper signals don't work here. The raw stream can't serve: `raw` is
cumulative, so a needle any earlier step printed matches instantly. Nor can "wait
for any new output" — the footer heartbeat redraws on ~1s, the same order as the
latency it would be covering.

## The other thing that got fixed: the PTY leak

`driver.ts`'s `kill()` skipped `proc.kill()` entirely when the child had already
exited, which is the normal case — a TTY scenario ends by sending Ctrl-C. node-pty
releases the ConPTY and its conout worker **only** from `kill()`, and on the
`useConptyDll` path it defers the worker disposal to an `_outSocket.on('data')`
callback that a dead child never fires. So every scenario left a worker thread
and a pseudoconsole alive for the rest of the run.

Measured directly: at the end of `--only-tty`, **39 of 39** conout workers were
undisposed, with 39 `MessagePort`/`PipeWrap` pairs still in
`process.getActiveResourcesInfo()`.

`kill()` is now unconditional and idempotent: it kills the proc, reaches in to
dispose the conout worker (the only way to release that thread deterministically),
and disposes the xterm `Terminal`. `onData` drops late data so a post-teardown
write can't hit a disposed emulator.

This is a leak fix, not the crash fix. It looked like it might reduce crash
frequency — 2/14 against a 2/6 baseline — but the difference is inside the noise
for those sample sizes, and the full suite still crashed 3 of 4 `npm test` runs
afterwards. It is kept because releasing what you allocated is correct on its own
merits, and because it makes `driver.test.ts`'s "second kill is safe after process
already exited" actually exercise the kill path instead of a no-op.

## The dead end: "no version has both"

Before the two-components insight landed, the crash was localised to node-pty
1.1.0's `useConptyDll` path and every escape from that path was measured. The
numbers stand; only the conclusion drawn from them was wrong.

| lever | segfaults | breaks |
| --- | --- | --- |
| baseline | 4/6 (`--only-tty`, instrumented) | — |
| deterministic teardown (the leak fix above) | 2/14 | nothing |
| `E2E_CONCURRENCY` 6 / 4 / 2 | 1/8 · 2/12 · 0/4 | wall time only |
| `useConptyDll: false` | 0/6 | `tty-blocklist-purge` hangs at the confirm prompt — *not* because Enter is undelivered |
| node-pty 1.2.0-beta.14 | 0/8 | 3–4 resize scenarios fail whenever other ptys are live |

All fourteen 1.2.0 betas were swept (`--only-tty`, one run each; then 10 runs on
the candidate). The crash fix and the resize regression appear to arrive together:

| betas | resize | segfault |
| --- | --- | --- |
| 1–5 | clean | not exercised enough to say |
| 6–9 | clean | **crashes** (1/1 each) |
| 10–11 | clean | **crashes** (beta.11: 3/10) |
| 12 | 1 scenario fails | — |
| 13 | 3 scenarios fail | — |
| 14 | 3–4 scenarios fail | 0/8 |

beta.11 is the newest build with working resize and it still crashes 3/10; the
first build that stops crashing (14) is past the regression. The inference —
"there is no version of node-pty that has both, so pinning is closed" — is the
error: the crash fix and the resize regression live in two *different* components
that happen to ship together, so the answer is beta.14 (crash) with the host
pinned back to 1.23 (resize), which no single version can express.

The beta was never a misconfiguration on our side: its `WindowsTerminal` drops the
`useConpty` parameter but still maps `opt.useConptyDll` to the right slot.

Also proposed here and **never built — don't build it**: sharding the TTY phase
across child processes and retrying a shard that dies on a signal, to contain a
crash that was believed incurable. The crash has a cure; don't trade it for a
green pipeline. The one part of that proposal worth keeping is already in: the
per-scenario progress line, without which a crash and a pass produce the same log.

## Do not redo

- Don't sweep node-pty versions one at a time. Diff `lib/`, `src/` and
  `third_party/conpty` across the boundary first — beta.11→beta.12 changed *only*
  the vendored host, and beta.12→beta.13 (the actual crash fix) changed only C++.
- Don't raise `quietMs` or the poll budget to chase a resize failure. If a
  `tty-resize-*` scenario is flaky, check the pin marker first.
- **Capping `E2E_CONCURRENCY` does nothing.** The rate is flat across 8/6/4 once
  the samples are pooled. An early 0/6 at 4 looked like a trend and regressed to
  2/6 on the next batch.
- **Synthetic repros do not reproduce it.** Three scripts, ~25 runs: N up to 60
  ptys, heavy continuous child output, a mix of exited and still-running children
  at teardown, xterm in the data path, and forced `gc()` between batches to test
  whether GC of an unkilled `IPty` finalizes native handles under a live worker.
  Zero crashes. Only the real concurrent suite reproduced it.
- **A single scenario in a tight loop** (`--only=<name>`, 20×) never reproduces.
- Node's `--report-on-fatalerror` produces no report for this crash; it is a
  native access violation, not a V8 fatal error.
- **Not the blocklist-purge feature.** Worth stating because the two got
  conflated — the EPERM bug in [29-07-2026d.md](29-07-2026d.md) *was*
  blocklist-specific (those are the only two scenarios calling `seedModels`).
  This one is not. With `tty-blocklist-purge.e2e.json` deleted outright,
  `--only-tty` still segfaulted **4/8**. Any 38 TTY scenarios reproduce it;
  removing the feature buys nothing.

## Measurement notes

Exit codes were recorded per run throughout: a crashing run and a clean run
produce the same log, so nothing else distinguishes them. Two things cost time
here and are worth knowing:

- Backgrounded sweeps were killed mid-loop twice while their `run-e2e` children
  kept going, so two suites competed for the box unnoticed. Check for stray
  `run-e2e` processes before trusting a timing measurement.
- A probe child that never reads stdin never receives `'resize'` on Windows at
  all: libuv surfaces console size changes through the console **input** buffer.
  freecode reads stdin in raw mode; a probe must too, or it measures nothing.
