# Bug Log

## `local state is incorrect…` re-bootstrap: documented fix never landed

**Symptom:** Recurring `ERROR libsql::sync: local state is incorrect, db file exists but metadata file does not` on synced launches, followed by a few-second stall while libSQL re-pulls the whole DB. Same symptom as `docs/bug log/27-06-2026.md`.

### Root cause

The 27-06 root cause was correct (a tokenless run opens the sync replica as a plain client, dirtying its `-info` metadata and forcing a re-bootstrap on the next tokened run). But the **fix and its "Coverage" described in `27-06-2026.md` were never committed** — the doc got ahead of the code. `git log -- src/providers/db.ts` shows the `-info`-decline logic never existed, and `db.test.ts` had no such test. The commit that added the 27-06 log (`84b27db`) only touched `src/cli/eval-menu.ts`. So the bug was still live: distinct from the already-fixed `WalConflict` crash (`26-06-2026.md`), and — critically — **not** something `isReplicaConflict()` should ever match, because `local state is incorrect` is never *thrown* (libSQL self-heals internally); broadening that regex would trigger a destructive wipe of a replica about to be legitimately re-pulled.

### Fix

Implemented the 27-06 design for real, in `src/providers/db.ts`:

- New `isSyncReplica(url)` = "an `-info` sidecar exists". In `openAndPrepareClient`'s **no-tokens branch**, if `isSyncReplica`, **decline to open** (leave `client` null) instead of opening a plain client over the replica.
- `doInit` now guards the null-client case explicitly (`if (client) { load… } else if (cache === null) cache = {}`), so a decline is a **calm** degrade — it does not fall into the `catch` that logs "Store init failed" with a stack.
- `isReplicaConflict` and `wipeLocalDb` exported for unit testing; the `/WalConflict/i` regex left deliberately narrow.

### Coverage

- `tests/providers/db.test.ts`: plants a **valid** db (with a persisted `groq:llama` row) + an `-info` sidecar, no tokens → asserts the cache is empty (row NOT loaded ⇒ declined), `SELECT 1` throws "DB not initialized", and the db + `-info` bytes are untouched. Verified it **fails** without the fix (plain client loads the row). Inverse test: no `-info` + no tokens still opens a real plain client. Pure-unit tests for `isReplicaConflict` (matches `WalConflict`, **not** `local state is incorrect`) and `wipeLocalDb` (removes all sidecars incl. `-info`).
- `tests/providers/db-sync-recovery.test.ts` (new): mocks the one otherwise-unreachable path — `@libsql/client` — to script `sync()`. Asserts `WalConflict` → close + wipe (`-info` gone on real fs) + reopen + re-pull, and a transient network error → same client kept, `-info` preserved, run offline. This is the `openAndPrepareClient` sync-error branch that previously had zero CI coverage.
