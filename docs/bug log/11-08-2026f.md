# Concurrent snapshots collided in the shadow repo's object database on Windows

**Files:** `src/snapshots/shadow-repo.ts`, `src/snapshots/index.ts`

`tests/snapshots/index.test.ts > lets concurrent sessions snapshot the same project without
colliding` failed under a full `npm test`, and passed on its own:

```
error: unable to write file …/objects/5a/72eb2edc…: Permission denied
error: untracked.txt: failed to insert into database
fatal: adding files failed
```

**Cause.** The scratch-index design removed the `index.lock` contention between concurrent
sessions, but the *object database* is still shared — and it is not lock-free on Windows.
Three racers snapshotting one project hash the same content, so they write byte-identical
loose objects. Git writes an object to a temp file and links/renames it into place; POSIX
overwrites atomically and git treats the collision as success, while Windows cannot rename
over the existing object (loose objects are read-only) and the call fails `EACCES`. The
snapshot hook swallows failures, so in real use this leaves a session silently unprotected —
and it is likeliest on a session's *first* write, the only time `takeSnapshot` fires, because
a cold shadow repo writes every object in the tree at once.

**Fix.** `retryingObjectWrites` in `shadow-repo.ts` — up to 3 attempts with a short backoff,
gated on the error carrying *both* a permission failure and `unable to write` / `failed to
insert into database`, so a genuinely read-only snapshots directory still surfaces on the
first attempt. On the retry the winner's object is on disk and git skips writing it. Applied
to the three calls in `takeSnapshot` that write objects — `add -A`, `write-tree`,
`commit-tree` — and deliberately not to `update-ref` or the restore path, which write no
objects and where a retry would re-run a partially applied change.

Rejected an in-process mutex: the unit test races inside one process, but the real case is
two freecode processes in one project (`CLAUDE.md`'s standing rule is to delegate to
`freecode -p --edit`). A lock would have turned the test green and left the bug intact.

**Verified** with a standalone harness rather than the suite, since the suite reproduced it
only under load: N concurrent `takeSnapshot` calls against a fresh project per round.
Pre-fix, 2 failures in 20 rounds at concurrency 3 — spread across the run, not confined to
the first round. Post-fix, 0 in 120 rounds at concurrency 5, with the retry log line firing
four times: the collision still happens and is absorbed, which is the evidence that matters.
A green run alone would only have proved the timing was perturbed.
