# `-p` ran a turn on the literal prompt `--stats`, because argv had no notion of a wrong argument

**Files:** `src/index.ts`, `src/cli/args.ts` (new), `tests/index.test.ts`, `docs/commands.md`

A calling agent ran:

```bash
freecode -p --stats -m zen:big-pickle "what does this repo do"
```

It exited 0 and printed a plausible answer. The answer was to the prompt `--stats`.

**Cause.** Every scan in `src/index.ts` was `indexOf`-based, and nothing ever looked at a
token it did not go searching for. That is not one flag's quirk — the command hit three
independent silent drops at once:

- `-p` takes `args[promptIdx + 1]` unconditionally, so it swallowed `--stats` as its prompt.
- `-m` does not exist (`--model` is the only spelling) and no unknown-flag check existed, so
  it and its value vanished; the run used the configured default model.
- The real prompt was left as a bare positional, and positionals were not a concept — it was
  dropped too.

Cost the caller two calls and ~78k subagent tokens before the wrong prompt was spotted, which
is the actual severity here: the failure mode is a confident answer to a question nobody
asked, not a crash. Same class as [24-07-2026d.md](24-07-2026d.md) and
[04-08-2026.md](04-08-2026.md) — a path that reports success on input it never understood.

**Fix.** `src/cli/args.ts` holds the flag table (which flags exist, which take a value) and
`validateCliArgs`, one left-to-right walk that must account for every token *on the main
command line*. Three rejections,
each naming what it found: a value-taking flag whose value is missing **or is itself a flag**,
an unknown flag, and a bare argument no flag claimed. `src/index.ts` calls it before anything
else, so the later `indexOf` dispatch is now safe by construction — no flag's value can be a
flag, which is what made `indexOf('--model')` able to match the wrong side of a pair.

Rejected "refuse a `-p` value starting with `-`": it treats one symptom and leaves the other
two drops silent — `-m gpt` alone still runs the default model, and a stray positional still
disappears. It also breaks `-p "--stats is what?"`, which is a legitimate prompt. Gating on
the flag table instead is what keeps that prompt working (pinned by a test).

Rejected making the prompt positional (`-p` as a boolean). It would have been ergonomics, not
a fix: with `-m` still unknown, `-m X "prompt"` leaves two positionals and the first one wins,
so the reported command would still have run silently — on the prompt `X`. It also collides
with the `undo` verb resolved from `args[0]` and forces a `--` escape for dash-leading
prompts. The value-taking contract stays.

**Docs.** `docs/commands.md`'s flag section had never stated that a flag's value is the *next*
argument, and its examples put other flags after the pair while `docs/subagents/recipes.md`
puts them before — between the two, nothing said flags may not sit *inside* a pair. Now
stated, with both orders shown as the same command, plus a note that quotes are the shell's
(they make a multi-word prompt one argument and never reach freecode).

**Still open.** Subcommands are outside the walk: `src/index.ts` resolves `undo` from
`args[0]` and returns before validation, and `src/cli/undo.ts` still does
`args.includes('--list')`. Verified after the fix — `freecode undo --lst` exits 0, having
read `--lst` as a snapshot id. Same class, one surface further in.

**Verified** by `tests/cli/args.test.ts` (every rejection message, and that
`-p "--stats is what? explain"` is accepted) and `tests/index.test.ts`, which spawns the
reported command verbatim for exit 1 and the dash-leading prompt for a real run.
