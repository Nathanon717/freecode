# 25-07-2026d — Prompt-based tool mode advertised `spawn_agent`, a tool it does not build

## Symptom

Any model routed through the prompt-based tool protocol (`agent/parsed-tools.ts`) was told
it had `spawn_agent` and was actively encouraged to use it for large investigations, but no
such tool existed in that mode. A model that took the advice would emit
`<tool_call>{"name":"spawn_agent",…}</tool_call>` and get back
`Unknown tool: "spawn_agent". … Available tools: read, create, edit, grep, shell_exec, list_dir`
— a wasted step, and a confusing one, since the system prompt had just listed the tool.

Affects every model with the `nativeTools: false` trait and any model run with the
`parsedTools` setting on.

## Cause

Two independent sources of truth for "what tools exist" that nothing kept in sync.

`buildSystemPrompt` (`agent/system-prompt.ts`) hardcoded `spawn_agent` in its
`Available tools:` line and in a HANDY TIPS bullet. `agentLoop` builds that prompt once,
before it knows which protocol the turn will use, and hands the same string to both
`streamWithRetry` and `runParsedToolsLoop`.

The native path passes a model-bound `spawnAgent` runner into `createTools`, so the tool is
real there. `runParsedToolsLoop` calls `createTools(confirmToolCall, toolRationale, true, readOnly)`
— four arguments, no runner — and `createTools` gates `spawn_agent` on that fifth parameter
being present. Its own `PARSED_TOOLS_ADDENDUM` tool reference correctly lists six tools and
omits `spawn_agent`, so the augmented prompt contradicted itself: the base said seven tools,
the addendum documented six.

Worth noting what this is *not*: the previously documented limitation, "if a real provider
lacks native tool calling the native sub-agent returns a graceful error string," described a
path that is essentially unreachable. When native tools fail, the turn switches to
`runParsedToolsLoop` and `runSubAgent` is never called at all. The real gap was that a whole
class of models silently cannot delegate.

## Fix

`buildSystemPrompt(loadAgentsMd = false, spawnAgent = true)` now gates both the tool list
entry and the delegation tip. The default preserves every existing caller.

`agent/loop.ts` rebuilds the prompt as `buildSystemPrompt(modelSettings.loadAgentsMd, false)`
immediately before entering `runParsedToolsLoop`, rather than reusing the native one. It is
rebuilt rather than computed up front because the fallback can be decided mid-stream, after
the native attempt fails.

Left alone deliberately: the fallback tool list inside `rejectedToolCall`
(`util/errors.ts`) still reads `read, create, edit, grep, shell_exec, list_dir`. It is used
only when the SDK error carries no list of its own, and it is shared with sub-agents, whose
real tool set is narrower still — adding `spawn_agent` there would advertise recursion to an
agent that cannot recurse.

## Coverage

`tests/agent/system-prompt.test.ts` — the existing "lists all available tools" assertions
pin the default, and a new case asserts `buildSystemPrompt(false, false)` contains no
`spawn_agent` while still listing the six tools the addendum documents. Without it, a future
edit that re-hardcodes the tool name into the prompt would pass the whole suite.

No new e2e: the tool map on the parsed-tools path is unchanged (it never had `spawn_agent`),
so the only difference is the prompt string, which the unit test now pins.
