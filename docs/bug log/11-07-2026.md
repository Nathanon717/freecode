# Bug Log

## Pre-tool preamble rendered after the tool call (out-of-order native transcript)

**Symptom:** On the native streaming path, a step's response text that precedes a
tool call (the "preamble") printed *after* the tool call header, its preview, and
even the confirm menu — e.g. the transcript showed `create(grade.py)` / result /
`Approve` and only then `Let's make this change.`. The prior fix (`26-06-2026.md`)
stopped the preamble from gluing onto the *final* text, but left it one step out of
place. Only visible interactively, where `index.ts` routes the transcript to stdout
(the same stream as response text); scripted/eval runs keep transcript on stderr, so
scenarios captured the two streams separately and never saw the true order.

### Root cause

`streamWithRetry` (`src/agent/loop.ts`) drove display from two decoupled sources:
model text from the `textStream` for-await loop, and tool-call headers/results as a
side effect of each tool's `execute` (`withLogging` in `src/agent/tools/index.ts`).
Verified against the real AI SDK (v3.4.33) with a `MockLanguageModelV1` probe: the
SDK invokes `execute` **before** the preamble text-delta reaches the stream
consumer. So `execute` drew its header while the preamble was still unconsumed —
no amount of "flush before the header from inside `execute`" can help, because at
that moment the text does not exist on the consumer side yet. The `onStepFinish`
flush from the earlier fix ran *after* `execute`, hence one step late.

### Fix

Drive display from the ordered `fullStream` instead of `textStream`. `fullStream`
delivers parts in true provider order (`text-delta…` → `tool-call` → `tool-result`),
so the consumer renders text, and on the `tool-call` part flushes the pending
partial line before the header is drawn. To stop `execute` from racing ahead, a new
one-slot rendezvous (`src/agent/tool-render-gate.ts`) makes `execute` wait at the
header until the consumer has processed that call's `tool-call` part.

Correlation is by **order, not id**: the AI SDK (v3.4) passes no tool-call id to
`execute` (probed: its options object is `{ abortSignal }` only). Since `execute`
runs are serialized (`withSerializedExecution`) and `fullStream` emits `tool-call`
parts in the same order, a plain counting semaphore pairs the Nth `execute` with the
Nth part. The gate is armed only around the native `fullStream` consumption, so the
prompt-tools loop, the fake-direct loop, and `/renderer` (which render tool steps
synchronously and emit no `tool-call` part) are unaffected. A safety timeout means a
lost release degrades to the old behaviour instead of hanging the agent.

Also handled: `fullStream` reports mid-stream failures as an `error` **part** rather
than throwing (probed) — the consumer captures it and re-throws after the loop so the
existing tool-use/retry `catch` logic still applies. Provider-level rejections
(e.g. tools-not-supported) still throw from `streamText`, unchanged.

### Coverage

- New `stdoutOrder` scenario assertion (`tests/harness/assertions/output.ts`): each
  substring must appear after the previous — the first way to pin transcript order.
  Unit-tested in `tests/harness/assertions.test.ts` (in-order pass, out-of-order and
  missing failures).
- `agent-preamble-flush.scenario.json` now runs with
  `env: { FREECODE_TRANSCRIPT_STREAM: stdout }` (so a single captured stream reflects
  true interleaving) and asserts `stdoutOrder: [preamble, create(grade.py), final
  text]`. The scenario harness's non-TTY branch now honours `scenario.env`
  (`tests/harness/run-scenarios.ts`). This scenario failed before the fix and passes
  after.
