# Bug Log

## FIXED — Inline `code` grey background bleeds across a terminal soft-wrap

**Symptom:** when an inline `` `code` `` span (grey background) sits near the right
edge so the terminal soft-wraps it onto the next physical row, the rest of that
wrapped row's whitespace also shows the grey background.

**Cause:** not a byte defect. The renderer emits correct ANSI — open bg, text,
`\x1b[49m` close. But it never wraps: it prints one logical line and lets the
terminal soft-wrap it. When the terminal crosses the right margin while a
background is still open, background-color-erase (BCE) paints the newly wrapped
row with that background; cells not later overwritten by text stay grey. The
stray grey is drawn by the terminal, not present in our output — so it can't be
stripped from the bytes.

**Fix (`src/cli/markdown-renderer.ts`):** prose now goes through `renderProse`
(`renderInline` + new `wrapStyled`). `wrapStyled` tracks open SGR groups and, at
the wrap column (`termWidth()`), hard-breaks the line *only when a style is open*:
close styles (`\x1b[0m`), real newline, reopen on the next line. The background is
therefore never active as the cursor crosses the margin, so BCE has nothing to
bleed. Unstyled prose keeps no style open at the boundary and is left for the
terminal to soft-wrap, preserving resize reflow for ordinary text. Tables and
code blocks are width-sized separately and are not routed through `wrapStyled`.

**Out of scope:** code-block lines longer than the terminal width share the same
latent BCE bleed (they are full-width grey by design); left for a follow-up.

**Coverage:** `tests/cli/markdown-renderer.test.ts` — asserts an inline-code span
straddling a forced 10-col width hard-breaks (first physical line ends in a bg
reset, background reopened on the next), and that unstyled prose is not broken.
The bug itself is a terminal rendering effect and can't be asserted from bytes;
the test asserts the fix (reset lands before the wrap).
