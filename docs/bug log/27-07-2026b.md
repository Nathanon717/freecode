# 27-07-2026b — Bare `vitest` on Windows: 6 failures, all test-side (a fixture that can't exist on NTFS, and PTY tests that were never meant to be in the run)

## Symptom

`vitest` (no args, watch mode) on Windows: 6 failed / 2165 passed. Green on Linux.

```
FAIL  tests/agent/tools/grep.test.ts > parses paths containing a colon
      expected 'No matches found' to contain 'we:ird.ts'
FAIL  tests/harness/pty/session.test.ts > start spawns a daemon and prints initial screen
      start exited non-zero: expected 1 to be +0
… plus screen/send/send-escape/stop, all cascading from `start`
```

Two unrelated causes that happen to share a platform.

## Cause 1 — the colon fixture cannot exist on Windows

The test writes `we:ird.ts` to assert that `--null` field separation parses a filename
containing rg's own `:` separator (the defect fixed in [25-07-2026.md](25-07-2026.md)).

`:` is not a legal filename character on Windows — it delimits an NTFS *alternate data
stream*. `writeFile(join(root, 'we:ird.ts'))` does not fail; it silently writes the content
into a stream named `ird.ts` hanging off a file called `we`. Probed directly:

```
write OK
dir listing: ["we"]
```

The needle lands in the ADS, `we` itself is 0 bytes, rg walks the directory and matches
nothing — hence `No matches found`. Nothing is wrong with `grep.ts`: `--null` is still
correct and still earns its keep cross-platform, where it also keeps match (`:`) rows
distinguishable from context (`-`) rows. The fixture the assertion needs simply has no
Windows equivalent.

## Cause 2 — PTY tests were never part of the unit run

`scripts/pipeline/pipeline.ts` has excluded both PTY files from `npm test` since they were
written (`PTY_EXCLUDES`, "require a real PTY"). They pass on Windows via the sanctioned
entry point — `npm run pty:test` → 2 files, 14 passed, 1 skipped.

The gap was that `vitest.config.ts`'s `include: ['tests/**/*.test.ts']` did not encode that
intent, so a bare `vitest` — the natural watch-mode command — collected them anyway. There
they compete with 114 other files at `maxWorkers = cores - 1`, and the daemon's startup
(tsx transform → spawn `dist/index.js` under ConPTY → `waitForText('for commands', 20_000)`
→ settle → up to 40 input-liveness probes) overruns its 20s budget, `process.exit(1)`s, and
the client waits out its 40s deadline reporting `Session never became ready`. The remaining
four tests share one session, so they cascade.

Measured standalone on the same machine: `start` completes in ~10s from a clean session dir.
The budget is fine; the contention is not.

## Fix

1. `it.skipIf(process.platform === 'win32')` on the colon test, with a comment recording the
   ADS behaviour — the obvious "why is this skipped?" cleanup would reintroduce a test that
   cannot pass.
2. Both PTY files self-skip unless `FREECODE_PTY=1`; `pty:test` now sets it via `cross-env`
   (already a devDependency).

`PTY_EXCLUDES` stays on top of the env gate rather than being replaced by it: the gate is a
`describe.skipIf`, which still *imports* the file, and importing `driver.test.ts` loads
node-pty's native binding. The excludes keep `npm test` from collecting them at all.

Adding the two files to `exclude` in `vitest.config.ts` was tried first and rejected — it
also removes them from collection under `pty:test`, whose CLI positionals are a filter over
the collected set, not an override. That run reports `No test files found, exiting with code 1`.

## Coverage

No `src/` change, so no new test. The verification that matters is that the gate skips
without silently emptying the suite:

- `npm run pty:test` — 2 files, **14 passed | 1 skipped**, identical to the pre-change
  baseline. (A broken gate would exit 0 with zero tests: green, and wrong. Check counts,
  not the exit code.)
- bare `npx vitest run` — 114 passed | 2 skipped, **2156 passed | 16 skipped**, 0 failed.
  Totals reconcile: the 6 failures became 15 skips (14 PTY + 1 already-skipped resize) plus
  the 1 colon skip.
- `npm.cmd test` — 114 files, 2156 passed | 1 skipped.

Not a clean sweep, and the honest record: one `npm test` run in the middle of this work
reported `Results: 51 passed, 1 failed` in the e2e section. The failing test's name was not
captured (`run-e2e.ts:392` prints the summary only on failure, and the tail shown at the time
did not include the per-test line). It did not reproduce in **9** subsequent full e2e runs,
nor in 5 isolated runs of the prime suspect — `tty-status-line-ticks`, the timing-sensitive
TTY test rewritten earlier the same day in [27-07-2026.md](27-07-2026.md) and still uncommitted
in this tree. So the suspicion is unconfirmed in both directions: it was never named and never
reproduced. Nothing in this change touches `src/` or any e2e fixture.

A separate one-off in the same batch: one run died with a bare `Segmentation fault` before any
test executed (4 lines of output, npm banner only). Node/tsx crashed at startup, not a test
failure — no assertion involved.

Both are logged here rather than chased, because a run that cannot be reproduced in ten
attempts cannot distinguish a fixed cause from a quiet one.

## Cause 3 — `npm test` stopped after e2e without saying so, and read as "unit tests were removed"

Reported straight after the above landed: a `npm test` run ended at

```
> freecode@0.1.0 test:e2e
> tsx tests/harness/run-e2e.ts --no-build


Total: 46.0s
```

No unit section at all — a fair reading of which is that the change above had dropped unit
tests from the pipeline. It had not. `scripts/pipeline/test.ts` iterated `SECTIONS`, broke on
the first non-zero status, and printed **nothing** about which section failed:

```ts
exitCode = result.status ?? 1;
if (exitCode !== 0) break;
```

A section that fails *loudly* is fine — vitest and the e2e harness print their own failures.
A section that dies *quietly* is not: the pipeline then stops after output that looks like a
pass, which is indistinguishable from the remaining sections having been deleted.

**What the timing proves.** On this machine the e2e section alone takes ~58s (measured over 6
consecutive runs). The reported **total** was 46.0s covering build + lint + docs + e2e — less
than e2e's own runtime. So e2e did not complete, and since `test.ts` only breaks on a non-zero
status, it exited non-zero partway through. That much is fact.

**What is not established.** *Why* e2e exited early is unconfirmed. Three candidates, none
verified:

- The `Segmentation fault` seen once in ~16 runs this session (4 lines of output, npm banner
  only) has the same output shape as the report. Suggestive, not proof.
- Contention with this session's own work: back-to-back e2e stress loops were running while
  investigating, and concurrent e2e runs share the `freecode-store-*` temp dirs and session
  dir — the same shared state behind the EPERM noise below. An overlapping run is a mundane
  cause of a fast non-zero exit.
- Unexplained detail arguing against all of the above: the pasted output carries **no
  `npm error` lines**. A non-zero `npm test` prints them in cmd.exe. Either they were trimmed
  from the paste, or the exit was 0 — and exit 0 does not fit a section that failed at all.
  Not resolved.

**What was ruled out.** The pipeline is not structurally broken and the FREECODE_PTY gate did
not remove unit tests. `npm test` from real cmd.exe runs the unit section normally — 114 files,
2156 passed, `EXITCODE=0` — over two runs, and `vitest.config.ts` is unmodified in git.

## Fix 3

`test.ts` now names the failing section and what never ran:

```
FAILED: e2e (exit 1) - stopping.
  Not run: unit tests.
```

Deliberately ASCII. The one shell where a stalled pipeline actually gets misread is classic
cmd.exe, where a non-UTF8 codepage can turn a `✗` into mojibake. Verified in situ by tripping
the real `test.ts` with a lint error from cmd.exe, which printed
`FAILED: lint (exit 1) - stopping.` / `Not run: docs, e2e, unit tests.`

It also reports `result.signal` separately, for a section killed rather than exited. Note that
branch is Linux-only in practice: `useShell` is true on Windows, so cmd.exe sits between and
converts a signalled child into an ordinary non-zero exit code. Confirmed by probe — a child
that `SIGTERM`s itself surfaces as `exit 1`, not as a signal. The exit-code path names the
section either way, which is the part that was missing.

The underlying segfault is **not** fixed and not diagnosed; it reproduced once in ~16 full e2e
runs. What changed is that it can no longer be mistaken for a pipeline that skipped its own
tests.
