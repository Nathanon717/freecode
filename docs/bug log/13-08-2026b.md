# A `-p --edit` run whose snapshot failed freed the review lock and told nobody

**Files:** `src/snapshots/auto.ts`, `src/cli/headless-prompt.ts`,
`src/snapshots/review-lock.ts`, `src/cli/checkpoint.ts`

`ensureSnapshot()` swallows every failure to the log, deliberately: refusing writes
because the safety net is unavailable inverts the point of having one. Under `-p`
the transcript is silenced, so that log reached no caller at all.

The consequence was not the missing message. `sessionSnapshotId()` returned
`undefined` for *two* different things — "no write tool ever fired" and "writes
landed and no snapshot covers them" — and `headless-prompt.ts` released the review
lock on `undefined`. So a run that changed the project while its snapshot store was
broken marked the project **free**, at the exact moment it was least reviewable, and
the next delegation started on top of it.

**Fix:** three states instead of two. `sessionSnapshot()` answers
`none | taken | failed`, and `settleReviewLock` does one thing per answer — free the
project, record the id, or keep the lock and report on stderr. The exit code still
belongs to the turn (a turn that succeeded did succeed) and stdout still carries only
the answer, so `$(freecode -p ...)` composes as before.

The old rationale for the conflation is written into the JSDoc this replaces: holding
a lock for a failed snapshot would "strand the project with nothing able to clear
it". Not true — `checkpoint accept` works with nothing snapshotted and is the
documented way out of a stuck lock.

**The second half was in `outstanding()`,** and it is why this is not just a message.
A bare `checkpoint diff`/`revert` picked its target by comparing snapshot timestamps
against the lock's `startedAt`. With no snapshot of the delegated run's own in that
set, it selected whatever an interactive session had taken — *after* the damage — and
reported a clean diff, then a successful revert, against a state nobody had reviewed.

Timestamps cannot separate the two, so the lock now carries the id
(`recordLockSnapshot`, written by the holder on its way out) and `outstanding()`
reads it. The timestamp walk survives only as the fallback for a run killed before it
could record one. When the lock says the snapshot *failed*, the bare verb is refused
outright — every snapshot in the store belongs to somebody else, so answering would
be worse than not — pointing at `git diff`, `checkpoint accept`, or naming an id
explicitly, which still works.

`recordLockSnapshot` is an update and never a claim: it refuses when there is no lock
to update and when the lock belongs to another pid. `claimReviewLock`'s exclusive
`wx` write is the whole mutual-exclusion mechanism, and a bookkeeping call able to
create a lock would undo it.

**Covered by** `tests/e2e/prompt-mode-edit-snapshot-failure.e2e.json`, which breaks
the store with `GIT_OBJECT_DIRECTORY` pointing at a directory that is not there. That
fails every shadow-repo git call while leaving the lock file — plain `fs`, no git —
claimable, so the run gets past its claim and dies at the snapshot, which is the
sequence the bug needs.

**Caught in review: the escape hatch could dead-end for the same reason R4 fired.**
Both new messages send the user to `checkpoint accept`, which calls `takeSnapshot`
first — and the failures that trigger R4 are mostly structural (unwritable store,
missing git, corrupt shadow repo), so `accept` throws too and returned 1 with the
lock still held and nothing further to try. Before R4 the lock was released there, so
the wedge is new. `claimReviewLock` already knew this shape and says so in its
`store-unwritable` branch; the R4 messages had dropped the caveat. Keeping the lock
is still right, so the fix is in `accept`'s catch: name the lock file path and say
deleting it by hand is the last resort. Same review also found `reportNoSnapshots`
answering "freecode takes one before an agent session's first write" for a project
the agent had already changed — it returns before `outstanding()` is consulted, so it
now checks the lock itself.

Also fixed while here: the `reason` on stderr is one line. A failed `git` rejection
stringifies to the whole invocation (`--git-dir`, `--work-tree`, the format string)
before the actual fault, so the sentence a reader needs — `fatal: not a git
repository` — was the one buried. The log still has the error entire.
