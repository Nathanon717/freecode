# A file another process held open survived `checkpoint revert` — silently

**Files:** `src/snapshots/locked-files.ts` (new), `src/snapshots/index.ts`,
`src/snapshots/shadow-repo.ts`, `src/snapshots/coverage.ts`, `src/cli/checkpoint.ts`

Once ignored files entered snapshot coverage ([12-08-2026f.md](12-08-2026f.md)), a
file the OS will not let git rewrite stopped being exotic: databases and caches are
exactly what a running process holds open, and they are all in scope now. `.freecode`
is excluded by name; a user's own `dev.db` cannot be enumerated the same way.

The plan predicted one bug here and there were two, the worse one unnoticed. Measured
against a file held the way SQLite holds one — `FILE_SHARE_READ`, readable so `add`
still stages it, but neither replaceable nor deletable:

| git must | git says | exit | what happened |
| --- | --- | --- | --- |
| **replace** a file it cannot | `error: unable to unlink old '<p>':` | 128 | `restoreSnapshot` threw; `checkpoint revert` printed `Error reverting snapshot:` and named nothing |
| **delete** a file it cannot | `warning: unable to unlink '<p>':` | **0** | **nothing at all** |

The second row is an agent-created file surviving a revert while git reports success
— the class of failure the containment plan exists to close. `runGit` discarded
stderr on a zero exit, so there was nothing to see.

**Two things the plan got wrong about the first row, both measured rather than
reasoned.**

Its proposed fix — "re-run the restore with those paths excluded from the pathspec" —
does not exist. `read-tree` takes tree-ish arguments, not a pathspec:

```
$ git read-tree -u --reset HEAD -- a.txt
fatal: Not a valid object name a.txt
```

And it is not needed, because **`read-tree -u --reset` is not all-or-nothing**. It
restores every other path — including ones sorting *after* the locked one — performs
its deletions, and then reports what it could not touch. "Aborts mid-restore, some
paths back and the rest not" describes the `.git` half ([13-08-2026.md](13-08-2026.md)),
where the index is being rewritten, not this one. So the restore has already happened
by the time the call fails; the only thing missing was that anyone heard about it.

**Fix:** new `src/snapshots/locked-files.ts` runs the worktree restore, reads stderr
in both directions (`runShadowGitCapturing` exists for this one caller), and returns
the paths git named. The tolerance is narrow on purpose, like
`isObjectWriteCollision`: only a failure whose every `error:`/`fatal:` line is one of
those unlinks is swallowed, since a missing ref or a full disk has *not* been shown
to leave the rest of the tree restored.

**A locked path is a failed revert** — exit 1, review lock kept, paths named — the
same treatment `.git` already gets, and against the plan's sketch of returning them as
ordinary warnings on an exit-0 revert. Those paths still hold the agent's content, so
releasing the lock would mark unreverted work reviewed and admit the next delegated
run against it. That is the mistake the `.git` half made in its first cut, one layer
up.

The warning names both ways out, because only one of them ever finishes. Re-running
works when the holder is transient — `read-tree -u --reset` is idempotent, verified —
and never converges for a dev server that holds its database for as long as it runs;
there the paths are the user's own and `checkpoint accept` is the honest end of the
review. This also answers the question [13-08-2026.md](13-08-2026.md) left open, and
answers it *against* borrowing the `.git` half's advice: "everything except `dev.db`
is back" is a true description of a project, where "everything except
`refs/heads/main`" is not a description of a git directory.

**Testing this needs a real lock,** so those cases are Windows-only and say so.
PowerShell holds the file at `FileShare.Read`; there is no portable substitute, since
POSIX advisory locks do not stop `unlink`. The share mode matters: `FileShare.None`
blocks reading, which fails the `add -A` staging step *before* the restore, and is a
different failure this does not claim to handle.
