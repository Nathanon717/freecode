# `rate-limit-probe.ts` silently probed nothing: stale `p.type === 'openai-compat'` filter

**Files:** `scripts/diagnostics/rate-limit-probe.ts`

Running `npm run rate-limit-probe` (with or without `--only`) printed no `skip
<id>: no <ENV_VAR>` lines, ran no probes, and reported "wrote 0 reports" —
with exit code 0, so nothing flagged it as a failure.

**Cause:** `d62da0f` ("drop the anthropic adapter, route it through
openai-compat") deleted `ProviderConfig.type: 'openai-compat' | 'anthropic'`
entirely, since every provider now routes through the one adapter. It updated
every other caller of `.type` but missed this script's candidate filter:

```ts
.filter(p => !p.paid && p.type === 'openai-compat' && SPECS[p.id])
```

`p.type` is now `undefined` on every entry, so `undefined === 'openai-compat'`
is always false — the filter reduces `PROVIDER_REGISTRY` to `[]` before the
per-provider key check (which is what prints the skip lines) ever runs. Empty
candidates, empty loop, `reports.length === 0`, no thrown error anywhere.

**Fix:** drop the now-meaningless `type` clause — every provider is
openai-compat by construction, so `paid` plus having a `SPECS[p.id]` entry is
the whole filter:

```ts
.filter(p => !p.paid && SPECS[p.id])
```

Verified with `--no-burst` (13 providers probed, real 200/401 data) and then a
full burst run (real 429s, `retry-after`, and recovery timing captured for
groq/llm7/cohere/cerebras/mistral/zai).
