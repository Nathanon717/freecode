# Bug Log

## ✅ RESOLVED (21-07-2026) — Terminal resize corrupts the screen. Shipped Option B.

**Fixed.** The resize handler no longer wipes to the banner unconditionally. See the
**Resolution** section at the bottom for exactly what landed and how it was verified;
the handoff below remains as the analysis record. TL;DR of the fix:

- **Transcript present:** non-destructive — reset the scroll region + redraw only the
  bottom UI; the terminal reflows the transcript itself (native scrollback preserved).
- **Fresh screen (banner only, no transcript):** redraw the banner responsively
  (`clearAndRedrawBanner`) — clean compact/full swap, no stale bottom-bar cells to
  reflow into a duplicate footer. Detected via `hasPostEpochContent()`.
- Removed readline's own `'resize'` listener in `index.ts` (the stray `> ` + `\x1b[0J`).
- Suggestion overlay open on resize: scrub its reflowed-in stale rows from the buffer.

### TL;DR for whoever picks this up

- **Bug:** resizing the terminal (a) wipes the on-screen transcript and repaints the
  startup banner ("home page" reset), and (b) during fix attempts, mangled the
  footer/input bar and dropped the banner. Both are the same underlying fragility.
- **Root of the difficulty:** the transcript is *not modeled* by the app (the
  terminal owns it, via a scroll region — this is what gives native scrollback). Only
  the bottom bar is modeled, pinned with **absolute** cursor positions that all become
  invalid the instant the terminal resizes and reflows.
- **What the bug actually is:** narrow. The terminal already reflows the transcript
  correctly for free. The *only* broken thing is repositioning the pinned bottom bar.
- **Decision: Option B — harden the bottom-bar redraw in place, keep native
  scrollback.** Ink/full-ownership (Option A) was rejected: it would break the
  scrollback UX the codebase deliberately protects, and means rewriting ~2,900 LOC
  across ~12 TUI files incl. all raw-ANSI menus/pickers. Not worth it for a narrow bug.
- **Do NOT** reintroduce: transcript reconstruction from `screen-buffer.ts`'s rolling
  buffer (lossy, width-baked), or a full `\x1b[2J` + banner redraw (destroys transcript).

---

### How rendering works (the crux — internalize this)

Two layers, only one modeled:

- **Transcript** (banner, agent output, command results): printed into an ANSI
  **scroll region** with plain `console.log`/`stdout.write`, then *forgotten*. The
  terminal owns those cells. Deliberate — it's what gives real native scrollback
  (mouse-wheel history). `screen-buffer.ts` keeps an incidental ~150-line rolling
  buffer, but that's for the slash-suggestion overlay repaint, **not** a source of
  truth (capped, and stores lines already word-wrapped at the current width).
- **Bottom UI** (footer + input box): fully modeled. `drawFooter`/`drawInputArea` in
  `src/cli/terminal-ui.ts` re-derive it from state and pin it to the bottom rows via
  the scroll region, using **absolute** cursor positioning
  (`moveTo`, `setScrollRegion`, `lastReservedRows`, `footerRowCount`).

On resize the terminal resets the scroll region to full and reflows all cells
(including the previously-drawn footer cells) to positions the app can't observe.
That is the entire problem surface.

Native scrollback is an explicit, defended value here: see the Termux snap-back
comments in `terminal-ui.ts` (~lines 59, 335) and the whole idle-write-suppression
system (`lastFooterOutput`), which exists solely to avoid fighting a user who scrolled
up. **Any fix must preserve scrollback.**

### Approaches already tried, and why each failed

1. **Baseline (still in tree): on resize, clear screen + redraw banner**
   (`clearAndRedrawBanner`). No artifacts, but throws away the visible transcript →
   the reported bug.
2. **Reconstruct the transcript from `screen-buffer`'s rolling buffer and repaint it
   into the new scroll region.** Failed: buffer is capped at 150 lines and stores lines
   already wrapped at the *old* width; re-deriving screen position is lossy → banner
   landed at the wrong row, spacing off. Wrong layer. Abandoned.
3. **Leave transcript to native reflow; on resize only re-establish the scroll region
   + redraw the bottom UI; unregister readline's resize listener.** Correct model, but
   the footer/input bar came out **mangled** and the banner vanished.
   **Not fully diagnosed before revert.** Leading hypothesis: the bottom UI was redrawn
   against half-transitioned geometry — `drawFooter`/`drawInputArea` compute against
   `rows()`, `lastReservedRows`, and the live scroll-region state, and if the scroll
   region / `lastReservedRows` were set at the wrong moment (or `drawBottomUI` emitted
   multiple non-atomic writes while geometry was inconsistent), rows land wrong. This
   is almost certainly a **fixable redraw-ordering bug, not a wall.** Confirming this is
   step 1 of Option B.

### Interference to handle: readline's resize refresh (this part WAS correctly diagnosed)

`src/index.ts` creates a process-wide readline interface
(`createInterface({ input: process.stdin, output: process.stdout })`). Node's readline
refreshes its line editor on terminal resize — `_refreshLine` → `_writeToOutput`, using
its default prompt `'> '` — **even while paused**, and also emits `\x1b[0J`. freecode
renders its own bottom UI and only uses readline for `rl.question` (menus/approval), so
this refresh is pure interference: it scribbles a stray `> ` across the reflowed
transcript, one more per resize. Confirmed via stack trace
(`node:internal/readline/interface` → `onresize` → `_writeToOutput`).

Fix (part of Option B): right after `createInterface`, remove readline's own `'resize'`
listener. Diff the listener set to identify it without disturbing freecode's own handler:

```ts
const before = process.stdout.listeners('resize');
const rl = createInterface({ input: process.stdin, output: process.stdout });
for (const l of process.stdout.listeners('resize')) {
  if (!before.includes(l)) process.stdout.removeListener('resize', l as () => void);
}
```

Note: freecode's own resize handler lives in `terminal-ui.ts` and is registered at
module import time (index.ts imports `terminal-ui` at ~line 67, before `createInterface`
at ~line 81), so it's already in `before` and won't be removed. Verify this ordering
holds. rl is only used for `rl.question` rendering, which sets its own prompt when
invoked — dropping the resize refresh only means readline won't reflow its question
line mid-resize (rare, cosmetic; freecode redraws anyway).

### Option B — the plan to implement

Target: `src/cli/terminal-ui.ts`, the `process.stdout.on('resize', ...)` handler
(debounced 32 ms). Plus the readline one-liner in `src/index.ts`.

1. **Do not touch the transcript.** No clear, no banner redraw, no buffer repaint.
2. Reset the scroll region to full, then **recompute ALL geometry fresh** from the new
   `rows()`/`cols()` — do not trust cached `lastReservedRows`/`footerRowCount`; set them
   from scratch.
3. Set the new scroll region, **then** redraw the bottom UI as **one atomic write**
   built against the final geometry, so nothing paints while geometry is inconsistent.
   (`drawFooter`/`drawInputArea` already clear their own rows via `\x1b[2K`; make sure
   they're driven off the recomputed values, and consider composing footer+input into a
   single `process.stdout.write` for the resize path.)
4. Drop stale overlay state (`suggestionOverlayRows = 0`, `suggestionOverlayRestoreLines = []`)
   and force a footer repaint (`lastFooterOutput = null`) so the byte-identical skip
   doesn't suppress it. Call `_onResizeCallback?.()` last so a pinned picker repaints on top.
5. Remove readline's resize listener (snippet above).

**Known residual risk to characterize (not necessarily fix):** on a *height increase*,
the old footer may reflow up into the transcript as one stale line — you can't locate
it post-reflow to erase it. Decide empirically: accept it, or hard-clear just the
reserved bottom band. **This is the single thing a real-terminal test must answer.**

- Resize is PTY-level; `npm test` excludes PTY, so a green suite proves nothing here.
- Drive the **real TUI**. A `pty resize --cols N --rows N` harness command was

  node-pty `resize` + xterm `resize` in `tests/harness/pty/driver.ts`, a `resize` RPC

- Test matrix: height-grow, height-shrink, width-cross-82 (compact/full banner

- **Decision gate:** if after Option B the only defect is one stale footer line on

  *that* is the real signal to reconsider Option A (Ink/full-ownership).

### Why not Option A (for the record)

Ink/alt-screen makes resize trivial but: (a) breaks native scrollback (the defended UX)
unless you thread committed output through `<Static>`, which fights Ink's stdout
ownership against the 9 raw-ANSI keypress surfaces (menus, pickers, tool approval);
(b) ~2,900 LOC rewrite across ~12 files, weeks of work, high regression risk; (c) fixes
the narrow resize bug no better than a correct Option B while breaking working features.
Revisit only as part of a deliberate full-TUI rewrite.

## Resolution (21-07-2026)

Shipped Option B, driven by a re-added `pty resize --cols N --rows N` harness command
(`driver.resize()` → node-pty `resize` + xterm `resize`, a `resize` RPC, a CLI case),
which delivers a real SIGWINCH and makes the bug observable end-to-end.

**What landed** (`src/cli/chrome/bottom-ui.ts` resize handler, `src/index.ts`,
`src/util/screen-buffer.ts`, `src/cli/render/banner.ts`):

1. The handler branches on `hasPostEpochContent()` (new; true once any transcript has
   been printed since the overlay epoch):
   - **Transcript showing (or a pinned menu owns the screen):** non-destructive. Reset
     the scroll region to full, re-establish it for the new geometry, redraw only the
     bottom UI. The terminal reflows the transcript itself. Nothing is wiped.
   - **Fresh/startup (banner only):** `clearAndRedrawBanner()` — the banner *is* what's
     showing, so redraw it responsively (compact/full by width). A full clear here is
     correct and, crucially, leaves no stale bottom-bar cells to reflow into a duplicate.
2. Readline's own `'resize'` listener is stripped right after `createInterface`
   (`index.ts`) by diffing the listener set — it was emitting a stray `> ` + `\x1b[0J`
   across the reflowed transcript on every resize (the "part correctly diagnosed" above).
3. Suggestion-overlay-open-on-resize: the overlay's cursor-addressed rows reflow into the
   transcript as stale duplicates. The scroll region is repainted from the screen buffer
   (which holds clean transcript only — overlay writes carry cursor control and are never
   buffered) to scrub them. Runs only on the transcript path, not with a pinned menu.

**On the "residual stale footer" the handoff flagged:** it turned out to be a *full
duplicate footer block* (not one line), reproducible on **fresh-session** height-grow and
width-shrink — the wide bottom-bar border rows reflow/wrap and the newly-drawn footer
doesn't land on them. The epoch split dissolves it: a fresh screen takes the
`clearAndRedrawBanner` path (full clear, no stale cells), and once a transcript exists the
reflowed footer is overwritten by transcript flow rather than sitting alone under the
banner. No band-clearing heuristic was needed.

**Why `hasPostEpochContent` rather than pure always-non-destructive** (which an early
review leaned toward): empirically, always-non-destructive left fresh sessions with an
ugly terminal-reflowed FULL banner *and* the duplicate footer, and repainting the scroll
region from the buffer blanks the banner entirely (it is pre-epoch, excluded from the
buffer by design). The only misclassification the epoch split can make is treating the
transient startup blocklist-purge notice as "no transcript" and redrawing the banner over
it on resize — benign (it is disposable startup chrome, not user content).

**Verified** via the PTY harness across the full matrix — height-grow/shrink,
width-cross-82 (compact↔full boundary), width-grow/shrink, repeated resizes, plus the
eval menu, the slash-suggestion overlay, and a post-transcript session: transcript
preserved, single clean bottom bar, no stray `>`, no banner wipe when a transcript is up,
and a clean responsive banner when it is not. Coverage: `driver.test.ts` resize case,
`screen-buffer.test.ts` for `hasPostEpochContent`/`getScreenBufferScrollRegionLines`.
