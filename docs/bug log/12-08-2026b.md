# `checkpoint revert` reported history rolled back while leaving the user on the agent's branch

**Files:** `src/snapshots/index.ts`, `src/cli/checkpoint.ts`

Found during a security audit of `checkpoint` and `shell_exec`, but this is not
an attack — it fires for an honest agent. A delegated `freecode -p --edit` run
that does the ordinary thing:

```sh
git checkout -b agent-work
git commit -am "work"
```

leaves `freecode checkpoint revert` printing `Branch main rolled back to
a1b2c3d4.` while the user is still standing on `agent-work`, at the agent's
commit, with the agent's history in front of them. Files were restored, so the
tree looks plausible; only `git status` says otherwise.

**Cause:** two independent defects in the same block.

`restoreSnapshot` moved the *branch ref* and nothing else:

```ts
await runProjectGit(projectRoot, ['update-ref', `refs/heads/${meta.branch}`, meta.head]);
```

`HEAD` is a symbolic ref. Rewriting `refs/heads/main` underneath a HEAD that
points at `refs/heads/agent-work` changes nothing the user can observe — the
recorded commit is restored to a branch they are not on. Only `symbolic-ref`
moves the checkout, and it was never called. A snapshot taken on a detached HEAD
had no path at all.

Second, the whole head-restore was nested inside `if (existsSync(savedIndex))`,
which answers a different question — "was there an index copy to put back" —
so a repo missing its index copy had HEAD silently left alone.

**Fix:** extracted `restoreHead`, called from the top level of `restoreSnapshot`
rather than from inside the index branch. It writes the branch ref *and*
`symbolic-ref HEAD`, uses `update-ref --no-deref HEAD` for a snapshot taken
while detached, and warns instead of throwing when the recorded commit is no
longer in the object store (`git gc --prune=now` after the agent deleted the
refs holding it collects it — the files are already back, so failing the whole
revert would be worse).

The near-miss worth recording: the first version of the fix returned

```ts
return (await runProjectGit(projectRoot, ['rev-parse', 'HEAD'])).trim() === head;
```

as `headRestored`, which is true on *every* revert — including the overwhelming
majority where HEAD never moved and nothing needed restoring. That would have
made the CLI announce a rollback every time, which is the same class of lie this
entry is about, pointing the other way. `tests/snapshots/index.test.ts:104`
("leaves history alone when the agent never moved HEAD") caught it.

`headRestored` means *history was rolled back*, not *HEAD is now correct*. The
mutations are therefore gated on a pre-read: when HEAD is already on the
recorded branch at the recorded commit, `restoreHead` returns before writing
anything. That also keeps an ordinary revert from appending a reflog entry
claiming a rollback that did not happen. The CLI message follows the flag, and
now names the detached case rather than printing `Branch undefined`.

**Coverage:** the branch-switch case — the entire reason the extraction exists —
had no test. The two that existed covered "HEAD moved on the same branch" and
"HEAD never moved", and both passed while the bug was live, because `rev-parse
HEAD` is right whenever the branch ref is right. Three added, all asserting
`symbolic-ref` rather than only `rev-parse`:

- `brings HEAD back off a branch the agent created` — the reported bug.
- `reattaches a HEAD the agent detached`.
- `leaves HEAD detached when that is where the snapshot found it` — the
  `--no-deref` arm, which is reachable because `projectHead` records a detached
  HEAD as *no branch*. A plain `update-ref HEAD` would deref and leave HEAD
  symbolic, so this test is what holds that flag in place.
