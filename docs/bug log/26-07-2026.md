# 26-07-2026 — Rate-limit retry spammed the endpoint: `retryMaxWaitSeconds` truncated the server's `retry-after`, and concurrent calls each discovered the same limit alone

## Symptom

`scripts/diagnostics/map-drift.ts` — which fans ~107 source/map pairs across 8 concurrent
LLM calls on one API key — hammered a rate-limited endpoint instead of waiting it out. The
run neither made progress nor failed cleanly; it just kept firing requests that could not
succeed.

The suspicion going in was that the retry layer was missing on that path. It was not: the
default model (`zen:deepseek-v4-flash-free`) is an OpenAI-compatible provider, and
`createOpenAICompatProvider`'s `customFetch` has called `fetchWithRetry` all along. The
retry existed and was actively making things worse.

## Cause

Three defects, compounding.

**1. The cap was applied to the server's instruction.** `fetchWithRetry` computed

```ts
const rawDelayMs = retryHeader ? parseRetryAfterMs(retryHeader) : Math.min(2 ** attempt * 1000, options.maxWaitMs);
const waitMs = Math.min(rawDelayMs, options.maxWaitMs);
```

The second `Math.min` clamped a *server-supplied* `retry-after` to
`config.retryMaxWaitSeconds` (default 120s). A provider replying `retry-after: 600` got
waited on for 120s and retried — which cannot succeed, by definition, because the server
just said the window is 600s. Then again, and again, five times. `maxWaitMs` is a sensible
bound on backoff *we* invent; applying it to a value the server dictated turns a correct
wait into a guaranteed 429.

**2. No coordination between concurrent calls.** A rate limit is a property of the API key,
not of a request, but each in-flight call backed off in isolation. With 8 workers: all 8
hit the limit, all 8 sleep the same duration computed from roughly the same instant, all 8
wake together, all 8 fire. The backoff was per-request when the resource is per-key.

**3. Retry budgets multiplied.** `map-drift.ts` passes `maxRetries: 2` to `streamText`,
wrapping a fetch that already retries 5×; `openai-compat` throws the final 429 as an `Error`
carrying `statusCode`, which the AI SDK treats as retryable. Up to 18 HTTP requests per
pair, × 8 workers.

Separately, and the reason rate-limit handling felt inconsistent in the app generally:
`createAnthropicProvider` called `globalThis.fetch` directly (`anthropic.ts:205`). Anthropic
had **no** fetch-layer 429/503 handling at all — no `retry-after`, no countdown banner —
only the AI SDK's default `maxRetries`. Retry coverage was per-adapter, so whether an LLM
call backed off properly depended on which provider you happened to be on.

## Fix

In `adapter-http-retry.ts`:

- A `retry-after` is now honored in full, however long. `maxWaitMs` bounds only the
  `2^attempt` backoff used when the server sends no header. The outer `Math.min` is gone.
- A module-level `Map<providerId, notBeforeMs>` gates each provider. Any call that sees a
  429 publishes the hold *before* waiting it out; every call awaits the gate before sending.
  Holds only move forward, and the gate is re-read during a wait so a hold extended
  mid-wait still applies. Eight concurrent callers now back off once, together.
- `FetchWithRetryOptions` gained a required `providerId` to key that gate.
- Every wait is now abortable through `init.signal`. This is a direct consequence of
  removing the cap: `maxWaitMs` had been the only thing bounding a wait, and the sleep was
  a bare `setTimeout` with no escape. `map-drift.ts` passes
  `abortSignal: AbortSignal.timeout(300_000)` to `streamText`, which the AI SDK forwards to
  the custom fetch as `init.signal`; before threading it through, a 600s `retry-after`
  would run past that 300s deadline in full and only then issue a fetch with an
  already-aborted signal. The per-pair timeout had quietly stopped being a timeout.

`agent/loop.ts` passes no `abortSignal` to `streamText` today, so the interactive path is
unchanged by that last point — but it does mean a turn parked in a rate-limit wait is not
cancellable from the CLI. That gap is pre-existing (there is no abort plumbing to the loop at
all) and out of scope here; worth knowing it now matters more, since waits can be longer.

`createAnthropicProvider` now issues through `fetchWithRetry`, so retry/backoff is universal
across both adapter families — `resolveModel` has only these two branches, so this is
complete coverage rather than one more special case. Only the final response reaches the
usage/header/call-log branches, so retried 429s are no longer logged as errors.

Not changed, deliberately: the AI SDK's `maxRetries` in `loop.ts` and `map-drift.ts`.
Defect 3 was a multiplier on defect 1, not an independent bug — with `retry-after` honored
and the gate in place, an SDK-level retry now parks on the gate and fires only when the
window has actually elapsed. `maxRetries` also covers transport errors (`ECONNRESET`), which
`fetchWithRetry` does not retry, so zeroing it would lose real coverage.

`retryMaxWaitSeconds`' description in `commands/config.ts` said "Max seconds to wait before
retrying a rate-limited request", which is precisely the wrong mental model now — reworded
to name it as the no-`retry-after` backoff bound.

## Coverage

`tests/providers/adapters/adapter-http-retry.test.ts`:

- `retry-after: 600` against `maxWaitMs: 10_000` asserts the banner's target is 600s out,
  not 10s. This is the regression test for defect 1 — the old code passed every other test
  in the file while being wrong here.
- Two calls on one `providerId`: the second is issued after the first is already holding a
  30s window and is asserted *not* to have resolved 1s later, then to complete once the
  window elapses. Pins the gate.
- A 600s `retry-after` aborted 1s in via the request signal rejects promptly rather than
  sleeping out the window. Without the threaded signal this case hangs for the full 600s.

Both use fake timers; the pre-existing cases all wait 0ms, so a shared module-level gate
does not leak between them.

No e2e: the change is in HTTP retry timing, which e2e never exercises against a live
provider.
