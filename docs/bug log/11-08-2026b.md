# A Windows checkout counted one line more than Linux, so every map page came back dirty after `npm test`

**Files:** `.gitattributes`, `scripts/checks/line-budget.ts`, `tests/repo-encoding.test.ts`

Pull on Windows, run `npm test`, and 116 map pages were modified — 230 insertions,
230 deletions, every one of them a line count one higher than the committed value:

```
-  - [`conversation.ts`](agent/conversation.md) (59) — Session Controller
+  - [`conversation.ts`](agent/conversation.md) (60) — Session Controller
```

**Cause.** Two things had to be true at once, which is why it only showed up on one
machine.

Git for Windows sets `core.autocrlf=true` in the *system* gitconfig, so every source
file was checked out CRLF. The repo had a `.gitattributes`, but it named only three
files (`docs/providers.md`, `docs/commands.md`, `docs/scenarios.md`), so everything
else was left to autocrlf.

`countLines` in `line-budget.ts` strips the module header before counting, using:

```
/^(#![^\n]*\n)?\s*\/\*[\s\S]*?\*\/[^\S\n]*\n?\n?/
```

The two trailing `\n?` are meant to eat the newline ending `*/` **and** the blank
line separating the header from the first statement. Under CRLF the text after `*/`
is `\r\n\r\n`. `[^\S\n]*` matches whitespace-that-is-not-a-newline, so it consumes
the first `\r`; the first `\n?` takes the first `\n`; the second `\n?` then faces a
`\r`, does not match, and stops. The blank line survives as one extra counted line —
in *every* file, because every file has a module header. Hence the uniform `+1`.

Nothing was wrong with the generators. The count was reading a property of the
checkout instead of a property of the file.

**Fix.** Both layers, because either alone leaves a trap:

- `.gitattributes` now pins `* text=auto eol=lf`, which overrides `core.autocrlf`
  for every tracked path on every clone, so no config change is needed on any
  machine. `*.cmd` is pinned `eol=crlf` (cmd.exe is the consumer — a declared,
  stable exception rather than churn) and `*.gz` is `binary`.
- `countLines` normalises `\r\n` to `\n` before matching. A count must not depend
  on how the file was checked out even if a CRLF file appears some other way.
- `tests/repo-encoding.test.ts` gained a repo-wide CRLF guard alongside the
  existing BOM guard — same class of defect: invisible, and it makes the
  generators disagree with the tree.

Verified by what a checkout actually writes, not by what was on disk:
`git checkout-index --prefix=<tmp>/` with system `core.autocrlf=true` still set
produces LF for `.ts`/`.md` and CRLF only for `pty.cmd`.

Note the guard is *narrower* than the `.gitattributes` rule: it inherits
`TEXT_EXTENSIONS` from the BOM check, so `.py`, `.csv` and `.jsonl` are not
covered. A passing test is not proof the whole tree is LF.

## The phantom-dirty tree, and how to recover

Converting the working tree to LF costs every file its recorded size, and the trap
that follows is worth more than the regex above. Immediately after, `git status`
reported all 528 files modified while `git diff` reported nothing. Both were right:

| command | compares | result |
| --- | --- | --- |
| `git diff --name-only` | content | 3 — the real edits |
| `git diff-files --name-only` | index stat data only | 528 — stale sizes |

`git diff-files` vs `git diff` is how you tell stale-stat from real change. Confirm
with blob hashes if still unsure — `git rev-parse :<file>` against
`git hash-object --path <file> <file>` (the `--path` applies the clean filter):
identical hashes mean identical content.

`git update-index --refresh` and `--really-refresh` both print `needs update` for
every file, exit 1, and do not persist. The command that fixes it is:

```
git add --renormalize .
```

Files whose content is unchanged get their stat data rewritten without being
staged; only genuine edits land in the index. Anyone pulling this onto a second
Windows machine will meet the same 528-file phantom-dirty state once, and this is
the way out.

### `--renormalize` is not the whole recovery

Later the same day, `npm test` failed 276 times on the CRLF guard added above.
`--renormalize` normalises what goes **into the index**; it never rewrites the
bytes already sitting in the working tree. So the tree was left exactly as
`core.autocrlf` had written it, and `git status` stayed clean the whole time —
git compares post-normalisation, so a CRLF worktree file over an LF blob is not
a modification. The state is invisible to every command anyone thinks to run.

`git ls-files --eol` is the one that sees it: `i/lf w/crlf` is a stale file.

```sh
git ls-files --eol | sed -n 's/^.*w\/crlf[^\t]*\t//p' > /tmp/crlf-list.txt
while IFS= read -r f; do rm -f "$f"; done < /tmp/crlf-list.txt
xargs -d '\n' -a /tmp/crlf-list.txt git checkout --
```

Deleting first is what forces the re-checkout to run the filters; `git checkout`
on a file git already considers current is a no-op. Name the paths explicitly
rather than `git checkout -- .`, which would revert real uncommitted edits. One
file legitimately survives this: `pty.cmd`, pinned `eol=crlf`.

Nothing to commit afterwards, for the same reason nothing looked wrong before:
276 files changed on disk and `git status` reports exactly what it did before.
