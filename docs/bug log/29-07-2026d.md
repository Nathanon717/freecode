# 29-07-2026d — e2e cleanup left the seeded temp store behind (EPERM on Windows)

## Symptom

`npm run test:e2e` printed, not every run:

```
[cleanup] failed to remove tmpStore: Error: EPERM, Permission denied:
  \\?\C:\...\Temp\freecode-store-blocklist-purge-script-mode-...
```

Every test passed; only the temp dir survived. `process.exit(failed > 0 ? 1 : 0)`
counts assertion failures, so the run still exited 0 and the leak was invisible
except for the printed line.

## Cause

`blocklist-purge-*` are the only scenarios that call `seedModels`, i.e. the only
ones where the **harness process itself** opened a libSQL client on the store dir.

`@libsql/client` prepares a `SELECT 1 AS checkThatTheDatabaseCanBeOpened` probe
statement inside `createClient` (`sqlite3.js:52`), and the native `libsql`
`Statement` has no `finalize` — the underlying file handle is released only when
the object is garbage-collected. `client.close()` does not reach it. Windows
refuses to unlink a file with a live handle, so `rmSync` failed with EPERM.

Measured, 20 iterations each:

| variant | EPERM |
| --- | --- |
| `createClient` + `close()`, no queries | 20/20 |
| + 3s sleep before `rmSync` | 18/20 |
| + one forced synchronous `gc()` | 20/20 |
| + `gc()`, a tick, `gc()` | 0/20 |
| raw `libsql` `Database`, `exec()` only, no prepare | 0/20 |
| raw `libsql` `Database` with one `prepare()` | 20/20 |

That GC dependency is the whole story: a tight loop never collects and always
fails, while a full concurrent e2e run usually collects in time — hence "flaky".
It also rules out the two in-process fixes. Retrying `rmSync` doesn't help when
release needs a GC that may not come (3s wasn't enough), and a forced `gc()` only
works with a tick after it, because the N-API finalizer is deferred past the
collection — a timing-dependent fix for a timing-dependent bug.

## Fix

The seeding write moved to its own process: `seed-store.ts` now spawns
`seed-store-child.ts` (`node --import tsx`) and awaits it. Process exit releases
the handle unconditionally, so the harness process never opens the store at all
and there is no handle left to leak. `createSchema` reuse — the point of seeding
through the real schema — is preserved, unlike an exec-only raw-`libsql` rewrite,
which the table above shows would leak anyway on `createSchema`'s one
`PRAGMA table_info` prepare.

`run-e2e.ts` also routes its five temp-dir removals through `removeTempDir`, with
`maxRetries`/`retryDelay`. That is insurance for the dirs the *child CLI* held —
there, exit does release promptly and a retry covers AV/delete-pending lag. It is
not the fix for the seeded store.

## Coverage

No new automated test. The failure is a cleanup-path side effect that never
reaches the exit code, so a regression guard would have to assert on harness
stderr; the guard is the mechanism removal itself — no libSQL client is opened in
the harness process any more.

Verified by run: on unmodified HEAD, both of the two full e2e runs that didn't
crash printed the cleanup line; after the change, 0 of 12 runs (12 full, plus 6
`--skip-tty` and 6 `--only-tty`) printed one.

## Still open

`tests/store/db-schema.test.ts`, `db-load.test.ts` and `call-log.test.ts` open the
same `file:` clients on temp dirs and leak the same handle, but their teardown
already swallows it (`catch { /* OS will clean up */ }`), so they never fail —
they just litter `%TEMP%`.

Separately, and unrelated: `--only-tty` segfaults roughly 2 runs in 6, at the same
rate on unmodified HEAD. `--skip-tty` was clean 6/6. Not fixed here.

The guess recorded here — that `run-e2e.ts` ending on `process.exit()` races
node-pty's ConPTY teardown — was **wrong**; the crash lands mid-run, before the
exit path is ever reached. It is **fixed**: see [29-07-2026e.md](29-07-2026e.md),
which traces it to a data race in node-pty's C++, cures it with beta.14 plus a
ConPTY host pin, and along the way fixes the (real, separate) pty leak that
`driver.kill()` was leaving behind.
