# Sweep HTTP diagnostics counted every failure as a terminal 429

**Symptom:** `zen-north-mini-code-free.md`, from a `npm run dead-code` sweep, reported a
line that contradicts itself:

```
- requests: 111 for 111 files (200×111)
- 429 responses: 0 total, of which 39 were terminal (retries exhausted, surfaced as an error)
```

Zero 429s, yet 39 of them terminal. Every request had returned 200; all 39 failures were
`The operation was aborted due to timeout` at ~300.6s each — the per-unit
`AbortSignal.timeout(300_000)`. The same mislabelling inflated `zen-deepseek-v4-flash-free`
(3) and `zen-nemotron-3-ultra-free` (3).

**Cause (`scripts/sweep/http-probe.ts`):** the terminal count was
`outcomes.filter(o => o.verdict === ERROR_VERDICT)` — *every* error verdict, whatever caused
it — rendered on the 429 line as "of which N were terminal". A timeout, a transport drop and
an exhausted rate limit all produce an error verdict, so the number was right about how many
units failed and wrong about the only thing the line claimed.

This defeats the stated purpose of the section. `docs/sweeps.md` says the diagnostics exist
so "handled rate limiting (retried, then answered) can be told apart from terminal rate
limiting (retries exhausted, reported as an error)" — and it was reporting rate limiting that
never occurred, on a run where the interesting question (*why did 39 units die?*) was left
unanswerable.

**Fix:** a unit's *last recorded attempt status* decides the cause, not its verdict. Terminal
429s are now error-verdict units whose final attempt was a 429. A second line reports the
remainder (`failed files: N total, of which M failed for a reason other than rate limiting`),
and the `Terminal failures` block carries `last:` per unit — `429` an exhausted limit, `200` a
response that arrived and then stalled mid-stream, `transport` a connection that never
delivered one, `none` a unit with no attempt recorded.

On the north-mini-code data this yields 0 terminal 429s and 39 non-rate-limit failures, all
`last:200` — a response whose headers arrived and whose body never finished, which is a
different problem from a rate limit and now says so.

**Also fixed, same run (`scripts/sweep/sweep.ts`):** `nemotron`'s three errors printed
`[object Object]`. `describeError` used `error instanceof Error ? error.message :
String(error)`, and `String()` on a thrown plain object is `"[object Object]"` — the report
then carried no evidence at all, unlike the timeouts which were at least identifiable. Now
`describeThrown` falls back to `JSON.stringify` for non-`Error` throws.

**Coverage:** none added. Both paths are report *formatting* over module-level probe state
with no seam to inject attempts through, and the existing `tests/scripts/sweep-report.test.ts`
covers the report body rather than `diagnosticsReport`. Verified by re-running a two-unit
sweep and reading the rendered section; the failure paths were checked against the recorded
north-mini-code and nemotron data, not reproduced live.
