# Bug Log

## Blocklist-purge prompt STILL returns every launch — the delete never reached the primary

**Symptom:** After the 21-07 fix, one blocklisted model (`anthropic:claude-opus-4-1-20250805`)
kept re-triggering the "1 stored model is now blocklisted … Enter to delete" prompt on
every launch. Pressing Enter printed "Deleted 1 model." and it came back next launch. A
second model (an openrouter one) had stopped recurring, so the count went 2 → 1.

**Root cause:** two facts compounded.

1. **The row is stale and un-rewritable.** The Anthropic `/v1/models` API no longer returns
   `claude-opus-4-1` at all, so `runLiveProviderInit`'s `finish()` never sees it — the 21-07
   "apply blocklists before `saveProviderCatalog`" fix is irrelevant to it (nothing to
   filter). It just sits in the DB. A live-repro against a **local-only** copy confirmed
   purge + live init deletes it and never brings it back, so re-creation was ruled out.

2. **The delete never durably left the remote (Turso) DB.** `deleteModelRows` deleted on the
   **local embedded replica** and pushed via `c.sync()`, swallowing the push failure. A local
   delete is an un-pushed WAL frame; the per-launch catalog upserts keep advancing the remote,
   so that frame loses the push race and is discarded by the next launch's **WalConflict
   wipe-and-re-pull** in `openAndPrepareClient` — restoring the primary's copy. Every launch:
   `sync()` pulls the row back → `findBlocklistedStoredModels` matches `blocklist.json` →
   prompt. The `freecode.db-info` sidecar showing `"generation":40` corroborated the repeated
   wipe/re-bootstrap loop.

   The openrouter row went 2 → 1 only because its delete happened to win the push race in some
   session; same code, different luck.

**Fix (`src/store/db.ts`):** on a synced store, `deleteModelRows` now writes the delete batch
**straight to the primary** via a throwaway remote client (`readDbConfig`'s `syncUrl`/
`authToken`), then `client.sync()` pulls it local — no divergent local frame to be conflict-
wiped. It returns `true` when the delete is durable; `false` (primary write failed, e.g.
offline) makes `blocklist-purge-prompt.ts` tell the user it will retry next launch instead of
falsely printing "Deleted". Local-only stores (no sync configured, incl. tests) keep the plain
local `client.batch` delete, which is already durable.

**Coverage:** `tests/store/db.test.ts` — "deleteModelRows deletes the model row and all
children, returns true, and the delete survives reinit" (local path + cascade + return value)
and the empty-list no-op. The synced primary-write path needs a live remote and isn't
unit-tested; the existing `tty-blocklist-purge` scenario exercises the prompt end-to-end.

**Note:** the already-stale remote row is cleared the next time the user confirms the prompt on
a build with this fix (the delete now lands on the primary). Related: [21-07](21-07-2026.md).
