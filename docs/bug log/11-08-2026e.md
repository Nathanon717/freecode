# An e2e fixture used POSIX shell syntax, so `undo-snapshot-on-first-write` could only pass on Linux

**Files:** `tests/e2e/undo-snapshot-on-first-write.llm.json`, `tests/e2e/undo-snapshot-on-first-write.e2e.json`

The scenario reads the shadow repo back through the real git binary — the step that makes it
an end-to-end check rather than a mock. Its second scripted tool call was:

```sh
git --git-dir=$(echo "$FREECODE_HOME"/snapshots/*.git) --work-tree=. log --all --format=%s
```

On Windows the run reported only `missing: "The snapshot is there."` and `unexpected: "Error:"`.
The real failure was one line further in:

```
git: '$FREECODE_HOME/snapshots/*.git)' is not a git command.
```

**Cause.** `shell_exec` runs through `child_process.exec`, which uses `$ComSpec` — cmd.exe on
Windows. Command substitution, `$VAR`, and `*` globbing are all POSIX shell features that
cmd.exe does not have, so git was handed the text verbatim. Nothing about the snapshot
feature was broken: the snapshot was on disk the whole time, and the assertion never reached
it. The turn-3 `mustContain` then failed, which is what produced the unrelated-looking
`Error:` line.

**Fix.** The lookup runs through `node -e` — the convention already set by
`shell-failure-output.llm.json` and `tty-status-line-ticks.llm.json`, and the only interpreter
an e2e fixture can count on. It reads `FREECODE_HOME` from `process.env`, finds the `.git`
directory with `readdirSync`, and shells to git through `execFileSync`. Double quotes outside,
single quotes inside — reversing them breaks on Windows, where single quotes are not quoting
characters. When the lookup finds no shadow repo it prints the directory listing, so the next
failure names itself instead of looking like this one.

Note `--format=%s` survives cmd.exe: only `%VAR%` pairs expand, and a lone `%` is literal.

**Not fixed:** `shell_exec` still gets cmd.exe on Windows, so a model that writes POSIX
syntax meets this in real use too. That is a product question about which shell the tool
should spawn, not a test bug — the destructive-pattern list (`remove-item`, `set-content`,
`new-item`) says the Windows shell is deliberate.
