# `intent-drift` reported every map link in a `@role` as drift

**Files:** `scripts/diagnostics/intent-drift.ts`

The sweep reported four false `DRIFT` verdicts, all the same shape — a claim
links to a map page, the model notices no such string in the code:

```
src/agent/tools/index.ts        [wrappers.md](wrappers.md)        → "no `wrappers.md` is referenced"
src/agent/tools/wrappers.ts     [index.md](index.md)              → "`index.md` appears nowhere in this file"
src/cli/tools/tool-invocation.ts [tool-runner.md](./tool-runner.md) → "the code says `tool-runner.ts`, not a markdown file"
src/store/db.ts                 [db-schema.md](./db-schema.md)    → "imports `createSchema` from `./db-schema.js`"
```

Every one is correct by convention: `docs/map/` mirrors `src/` at identical
depth, so a relative link written in a module header resolves the same from the
page it is copied onto (`docs/map/README.md`, "Intent lives in the source file").
The count had grown 2 → 4 as more headers adopted the convention, i.e. the
detector was penalising the practice the map asks for — and a recurring known
false positive is what trains a reader to skim the report.

**Cause:** the system prompt never told the model these claims get copied onto a
map page. It sees a `.md` filename inside a claim about a `.ts` file, greps the
code for it, finds nothing, and fires the "named files the code no longer
contains" rule as designed.

**Fix:** one rule added to `SYSTEM_PROMPT`, written as a *translation* rather
than an exemption — a link is resolved from the page, so `X.md` names the
source module `X.ts` at that path, and the claim is audited against **that
module**. Pointing at a module that no longer owns the thing is still drift.

Scoping matters here, because the convention is wider than the four hits
(`grep -rn "\.md" src --include="*.ts"` on header lines finds ~12). Three
distinctions the rule has to make, each of which a looser phrasing gets wrong:

- Targets take `./`, bare, and `../` forms (`../cli/menus/model-screen.md`), so
  "sibling" is too narrow.
- A target that leaves the mirrored tree — `[providers.md](../../providers.md)`
  in `provider-registry.ts` — is a hand-written doc with no `.ts` twin, not a
  module. The model can't see it, so it can't audit it.
- The exemption is on **markdown link syntax only**. `system-prompt.ts`'s
  `@readwhen` names `AGENTS.md`/`CLAUDE.md` in prose, and those really are
  files; a blanket "`.md` in a claim is never real" would stop auditing them.

The rule also says the linking file need not import what it points at:
`wrappers.ts` links `index.ts` against the dependency direction, so an
import-presence test would re-fire that exact hit.

**Verified** on `zen:big-pickle`, one unit per run: the four hits plus the three
files the grep flagged as newly at risk (`provider-registry.ts`,
`system-prompt.ts`, `stdout-retry-sink.ts`) all come back `ok`, 7/7. Negative
control: `db.ts`'s link temporarily repointed at `[db-load.md](./db-load.md)` —
a module that exists but does not own the DDL — still fires, with the
translation made explicit: "the DDL lives in `db-schema.ts`; `db-load.ts` only
provides `loadFromDb`/`loadConfigFromDb`". The rule redirects the check, it does
not mute it.

Verdicts are not reproducible (`docs/sweeps.md`), so this is one clean pass, not
a proof.
