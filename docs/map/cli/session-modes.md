## Interactive Mode

- Uses raw stdin for prompt input via `runRawKeySession` (from `cli/menus/raw-picker.ts`), which owns the listener snapshot/restore and raw-mode lifecycle. This prevents readline from echoing typed characters into `process.stdout` and contaminating the screen-buffer epoch used by the suggestion overlay restore.
- Supports Ctrl+C exit, Enter (`\r`) submit, Tab completion, Backspace, Delete, Escape clear, printable character input, and Ctrl+letter shortcuts for footer toggles (Ctrl+A = Ask, Ctrl+R = Read-only).
- Ctrl+J (`\n`) inserts a newline, enabling multi-line input. Arrow keys (Left/Right/Up/Down), Home, and End move the cursor within the buffer; Delete removes the character at the cursor.
- Printable input goes through `handlePrintable`: typing `(` right after a valid tool name (see `cli/tools/tool-invocation.ts`) autofills the full argument skeleton (`read(path="", offset=, limit=)`) with the caret in the first value slot; typing `)` on top of a `)` types over it. Tab cycles forward through the value slots and Backspace at an emptied slot steps back (via `nextToolFieldCaret` / `toolFieldBackspace`); on submit `stripEmptyToolArgs` drops untouched slots.
- Shows inline command completion plus filtered suggestions from `slash-commands.ts`. Inline completion is suppressed for multi-line buffers.
- Starts an OpenAI-only preflight input-cost controller while editing, debounced from input changes and stopped on submit/cancel/teardown.
- Refreshes cached OpenAI daily spend snapshots for the footer when the bottom UI is active and the selected model is OpenAI.
- **Owns the footer `ctx` (context size) slot** — the *only* writer. `onAgentResult` reads `result.usage.promptTokens` (the provider-reported input tokens of the turn's last call = the whole history it resent) and passes it to `setContextUsage`, looking the model's `contextWindow` up via `providers/model-data.ts` `getModel`. Skips the update when no count was reported (a turn that errored before usage keeps the last good number). `applyModelChange` blanks it so a stale count is never attributed to a newly-selected model. See `cli/chrome/footer-status.ts`.
- **The `ctx` slot ticks up mid-turn.** `onStepUsage` (a `session-runner`/`command-dispatcher` hook fed by `agent/loop.ts`) fires at every step boundary of a multi-step tool turn with that step's own prompt tokens, so the count climbs while the agent is still working instead of jumping once at the end — each step resends a longer history, and the last value equals what `onAgentResult` would set. Both handlers share the `applyContextUsage` helper, which calls `drawFooter()` directly rather than waiting on the footer's 1 s refresh timer (a step that completes inside that second would otherwise never be shown). This works at all only because `teardownBottomUI` drops just the input area — the footer stays live for the whole turn. Note the count is *hidden* while a tool-approval prompt is up: `cli/tools/tool-approval.ts` deliberately blanks the footer rows so the confirm hint owns the last row. Covered by `tests/e2e/tty-status-line-ticks.e2e.json` (auto-confirm + a sleeping `shell_exec`, so the intermediate value is observable without a timing race).
- **The input bar stays up for the whole agent turn.** Only the tool-approval prompt takes it down. `beforeDispatch` still tears it down — that path is shared with slash commands and menus, which genuinely need the rows — so `beforeAgentCall` *restores* it (`setupBottomUI` + `drawBottomUI`) and then calls `parkCursorInScrollRegion()` to hand the cursor back for the turn's streaming output. It also sets the `turnActive` flag ([chrome/turn-state.md](chrome/turn-state.md)) *before* the redraw so the frame opens at its final height — `thinking…` row included — in one scroll rather than two; `afterAgentCall` clears it before its redraw so that row is released. Because the bar survives the turn, the toggle bar (a footer row gated on the input bar) is now visible mid-turn too. See [chrome/bottom-ui.md](chrome/bottom-ui.md#cursor-discipline-during-an-agent-turn) for why `drawInputArea` must not park the cursor while the flag is set. Covered by `tests/e2e/tty-thinking-label.e2e.json`.
- Tears down the bottom UI during command dispatch and tool approval prompts. The config editor and model picker manage their own teardown/restore via `cli/menus/menu-shell.ts`; the dispatcher's `runConfig`/`runModelMenu` are now thin calls that pass an `onRestore` closure (session footer refresh — `applyModelChange`/`resetBottomPromptState`/`refreshFooterDailySpend`/`drawBottomUI`) into `runConfigCommand`/`runModelCommand` for the shell to fire after `setupBottomUI`.
- `/model` without an argument opens `runModelCommand()` so interactive users can pick from configured provider models and detected Ollama models.
- Tool approval is Enter-to-confirm/Esc-to-deny (no selection menu — see `cli/tools/tool-approval.ts`); scripted mode's own choice is a two-item Approve/Deny listing, and either kind of denial can include user feedback to the agent. The Auto-run tools toggle (`getAskMode()` from `cli/chrome/toggles.ts`) controls whether approval is required at runtime; the initial state is seeded from `config.toolConfirmation`. The approval prompts and the scripted-choice parser live in `cli/tools/tool-approval.ts`; both modes import them. For precomputed read-only tools (which carry `preview.resultText`) interactive mode hands `confirmToolCallInteractive` a **thunk** `() => countTextTokens(resultText, getSelectedModel())` (from `tokenizers/count.ts`) for the hint's "+N tokens" / "+N tokens appx" line; the UI evaluates it on a deferred tick so the first (tokenizer-compiling) count can't stall the confirm controls. Model selection (`applyModelStatus`/`applyModelChange` → `warmTokenizers`) fires `preloadTokenizerFor(model)` on a timer so the count becomes exact once the model's tokenizer is compiled — deferred, and a no-op for models with no exact backend, so it never freezes startup. Interactive mode has no per-turn tool-call cap, and neither does the agent loop (`maxSteps` is unlimited — see [agent/loop.md](../agent/loop.md)); an interactive turn is bounded by the model finishing, context overflow, a provider error, or an Esc at a tool approval (below). Scripted mode still enforces a hard `FREECODE_MAX_TOOL_CALLS` budget by silently denying every call past the cap — that budget, not `maxSteps`, is what winds an over-running eval down.
- **Esc denies the call and ends the turn, without discarding it.** `confirmToolCallInteractive` resolves `{ approved: false, stopTurn: true }` — a denial, not a throw — and this mode passes it straight through; the wrapper adds nothing and keeps no per-turn flag of its own. `stopTurn` is honoured in the tools layer ([../agent/tools/wrappers.md](../agent/tools/wrappers.md#turn-stop-esc)): the ordinary `Tool call denied by user: …` result renders, and *then* `withTurnStop` throws, which is what stops the AI SDK taking another step. Everything the turn already did commits (the denial included, re-paired by `pairStoppedToolCalls`), the model is not called again, and the user is back at the input bar — the conversation resumes on their next message. `AgentLoopResult.stopped` reaches the dispatcher, which prints `Stopped. Send a message to continue.` rather than reporting the missing closing answer as an empty response. History: Esc originally threw `UserAbortError` and unwound the whole turn (`docs/bug log/05-08-2026.md`); the fix for that made it a plain denial, which let the turn keep running (`docs/bug log/05-08-2026b.md`).
- **Auto-approve token budget.** When `resolveModelSettings(model).autoApproveTokenBudget` is `> 0`, a tool call whose token count is strictly under it is approved without a prompt even in Ask mode. Gated on `isReadOnlyTool` ([../agent/tools/tool-names.md](../agent/tools/tool-names.md)) — deliberately *not* "any tool we can count", so a write can never be approved silently because its result happened to be measurable; `create` has a content preview and is measurable but writes a file, so it is never auto-approved at any budget. The comparison calls the same `getTokenCount()` thunk the hint would have displayed, so the number the user configures against is the number they would have seen (fallback estimate included). `0` is off.
- The Read-only toggle (`isReadOnly()` from `cli/chrome/toggles.ts`) is passed as `getReadOnly` on the mode object. When on, only `read`, `grep`, and `list_dir` are offered to the model — the write tools **and `spawn_agent`** are omitted from `createTools`, and the system prompt's tool list shrinks to match (`offeredToolNames`, see [../agent/system-prompt.md](../agent/system-prompt.md)). A turn already in flight when the toggle flips is caught by the `isWriteTool` denial in `confirmToolCall`, since its tool set was built before the flip. The headless `-p` mode reuses these same toggles rather than a parallel flag — [headless-prompt.md](headless-prompt.md).
